## 개요

`Etc/명세/상환.md`(대출 원리금 상환 코어 개발 명세, 15개 섹션)에 따라 `Core/repayment`를 신규 개발했다. 은행 앱의 화면 기능이 아니라 대출 코어에서 쓰는 상환 업무이며, 명세 §2.1의 구현 범위에 화면이 없고 §8이 REST API만 정의하므로 **백엔드만** 구현했다.

명세 §2가 요구한 대로 착수 전에 기존 프로젝트를 먼저 분석했고, 분석 결과와 모호한 업무 규칙 3건을 사용자에게 확인받은 뒤 개발을 시작했다.

### 확정한 결정 3건

| 항목 | 결정 | 근거 |
|---|---|---|

## 1. 착수 전 분석 결과 (명세 §2)

### 기존 대출 패키지 구조

`Mobile/bankEx`의 `loan/general`(MyBatis) + `loan/jeonse`(MyBatis) 2개 도메인.

### 명세 §6.1 LoanAccount와 기존 엔티티의 격차

기존 `LoanApplication`이 대출계좌 역할을 겸하고 있었으나 상환 코어가 요구하는 채무 버킷이 대부분 없었다.

| 명세 요구 | 기존 현황 |
|---|---|
| `principalBalance` | `remainingBalance` ✅ |
| `originalPrincipal` | `requestAmount`로 대체 가능 |
| `overduePrincipal` / `accruedInterest` / `overdueInterest` / `feeBalance` | ❌ 전부 없음 |
| `disbursementDate` / `maturityDate` / `version` | ❌ 없음 |
| `status` | `"실행완료"` / `"상환완료"` 한글 문자열 |

`LOAN_REPAYMENT_SCHEDULE` 테이블은 존재했으나 `APPLICATION_ID`가 `VARCHAR(40)`로 **전세대출 전용**이고, 납부 결과가 `PAID_YN` 한 글자여서 부분납부를 표현할 수 없었다.

### 기존 상환 서비스

`LoanRepaymentService.repay(loanId)` — **인자가 대출ID 하나뿐이고 금액을 받지 않는다.** 회차 금액을 스스로 계산해 전액 출금하는 구조라 부분상환·중도상환·전액상환·취소·멱등성이 모두 불가능했다. 상환 이력도 회차별 합계만 저장하고 항목별 배분 내역이 없었다.

### 공통 예외 구조 — 중요한 발견

명세 §12는 "현재 프로젝트의 공통 예외 구조를 사용"하라고 하는데, **사용자가 지정한 `Core/Screening`에는 공통 예외 구조가 없다.**

| 프로젝트 | 구조 |
|---|---|
| `Core/Screening` | ❌ `throw new IllegalArgumentException(...)` 2곳뿐, `@RestControllerAdvice` 없음 → 500 반환 |
| `Core/refinancing` | ✅ `BusinessException` + `ErrorCode` + `GlobalExceptionHandler` + `ApiResponse`, ErrorCode별 HTTP 상태 매핑 |
| `Mobile/bankEx` | ✅ 동일 패턴 (단 전부 400 고정) |

**`refinancing`의 구조를 차용했다.** 가장 최근 선례이고, §12가 요구하는 에러코드 구분과 §10이 요구하는 409 Conflict 반환에 그대로 맞는다.

### 차용한 기존 선례

명세가 요구한 세 가지가 `refinancing`에 이미 구현되어 있어 패턴을 그대로 가져왔다.

| 명세 | refinancing 선례 |
|---|---|
| §3.2 출금 게이트웨이 + Mock | `LoanRepaymentGateway` / `MockLoanRepaymentGateway` / `DemoScenarioAccounts` |
| §10 동시성 | `@Version` + 상태조건부 `updateStatusIfMatch` |
| §11 회계 이벤트 적재 | `AuditLog` Outbox |

### 충돌·중복 코드

- `LoanRepaymentService` / `LoanRepaymentHistory` — 이름과 역할이 겹치지만 독립 프로젝트라 물리적 충돌은 없다. 향후 어느 쪽이 정본인지 혼동 소지가 있다.
- `Screening`·`refinancing` 모두 엔티티를 각자 중복 정의하는 것이 이 저장소의 확립된 패턴이므로(Screening에 자체 `UserInfo`/`LoanApplication`, refinancing에 자체 `Customer`/`ExistingLoan`), 신규 프로젝트도 자체 `LoanAccount`를 정의했다.

## 3. 상환금 배분 정책의 동작 방식 (명세 §4·§5)

### 확장점

```java
public interface RepaymentAllocationPolicy {
    RepaymentAllocationResult allocate(RepaymentAllocationContext context);
    String supportedProductType();
}
```

`RepaymentAllocationPolicySelector`가 `LoanAccount.productType`으로 구현체를 고른다. 구현체를 Spring 빈으로 추가하고 `supportedProductType()`만 선언하면 자동 등록되며, 등록되지 않은 유형은 기본 정책으로 처리한다. 명세가 예시로 든 `GeneralLoan` / `JeonseLoan` / `DelinquentLoan` 전용 정책은 아직 추가하지 않았다.

**정책은 엔티티를 전혀 만지지 않는다.** 입력은 `ScheduleSnapshot` 레코드 목록이고 출력은 "무엇에 얼마 배분할지"의 목록이다. 덕분에 Spring 컨텍스트 없이 순수 단위테스트가 가능하다.

### 배분 순서

```
1. 계좌 비용 + 중도상환수수료                         (FEE)
2. 납부예정일이 도래한 회차를 오래된 순으로:
      연체이자 → 정상이자 → 연체원금 → 정상원금
3. 거래유형이 미래원금을 허용하면(PREPAYMENT/FULL) 남은 원금잔액
   아니면 미래 회차에 선납(정상이자 → 정상원금)
4. 남은 금액                                        (OVERPAYMENT)
```

회차 정렬은 명세 §5의 기준을 그대로 쓴다 — 납부예정일 오름차순 → 회차 오름차순 → 스케줄 ID 오름차순. 동일 납부예정일 스케줄이 여러 건이어도 처리 순서가 결정적이다.

### "도래 회차" 판정을 둔 이유

2단계를 `dueDate <= businessDate`로 제한했다. 명세 §3.6의 전액상환 구성 항목(정상원금·연체원금·정상이자·미수이자·연체이자·중도상환수수료·기타비용)에 **미래 이자가 없다**. 회차를 무조건 전부 순회하면 중도상환·전액상환이 아직 도래하지 않은 12개월치 이자를 선취해 전액상환 금액이 비정상적으로 커진다.

### 원금 한도 추적

중도상환 정책 ③은 원금잔액만 줄이고 스케줄 예정원금을 그대로 남긴다. 그래서 `sum(스케줄 미납원금) > 계좌 원금잔액`인 상태가 정상적으로 발생한다. 이 상태에서 회차별 원금 배분을 그대로 하면 원금잔액이 음수가 되므로, 배분 루프가 `principalLimit`를 하나의 한도로 추적해 회차 배분과 미래원금 배분이 함께 소비하도록 했다 (명세 §9).

### 명세 §4 예시 재현

```
납부금액 100,000원
비용 10,000 / 연체이자 20,000 / 정상이자 30,000 / 연체원금 50,000

→ 비용 10,000 · 연체이자 20,000 · 정상이자 30,000 · 연체원금 40,000
   남은 연체원금 10,000
```

단위테스트 `명세예시_10만원납부시_연체원금4만까지만배분되고_1만원이남는다`로 검증했다.

## 4. 도메인 모델과 테이블

명세 §6의 모델을 그대로 따르되 두 가지를 추가했다.

| 추가 필드 | 위치 | 이유 |
|---|---|---|
| `prepaymentFee` | `RepaymentTransaction` | FEE 배분액에는 기존 비용잔액과 이번에 발생한 중도상환수수료가 섞여 있다. 취소 시 **기존 비용잔액만** 되살리려면 수수료를 따로 알아야 한다 |
| `accountStatusBefore` | `RepaymentTransaction` | 명세 §3.7의 "대출계좌 상태 복원"을 추측 없이 하기 위해 거래 직전 상태를 보관 |
| `prepaymentFeeRate` | `LoanAccount` | §3.6이 전액상환 금액에 중도상환수수료를 포함하라고 하는데 명세에 산식이 없다. 계좌 단위 비율(%)로 두고 0이면 수수료 없음 |
| `productType` | `LoanAccount` | §4의 "상품 또는 상품 유형에 따라 정책을 선택" 키 |

### 테이블 (JPA `ddl-auto: create-drop`, H2)

```
LOAN_ACCOUNT              UK_LOAN_ACCOUNT_NUMBER, @Version
REPAYMENT_SCHEDULE        UK_SCHEDULE_ACCOUNT_SEQ (LOAN_ACCOUNT_ID, INSTALLMENT_NUMBER)
REPAYMENT_TRANSACTION     UK_REPAYMENT_TXN_NUMBER, UK_REPAYMENT_IDEMPOTENCY_KEY
REPAYMENT_ALLOCATION      (원장, 수정하지 않음)
OVERPAYMENT
ACCOUNTING_EVENT          (Outbox)
```

> Oracle 운영 반영 시 위 구조를 DDL로 수동 작성해야 한다. 이 프로젝트는 `schema.sql`을 쓰지 않고 JPA가 스키마를 만든다(`Screening`·`refinancing`과 동일).

### 금액 타입

모든 금액은 `BigDecimal` **scale 0 / HALF_UP** 이며 `common/util/Money`를 통해서만 다룬다. `double`·`float`은 쓰지 않는다 (명세 §9).

### 집계 필드는 감산이 아니라 재집계

`LoanAccount`의 `overduePrincipal` / `overdueInterest` / `accruedInterest`는 배분 반영 후 **스케줄에서 다시 합산**한다. 감산 방식이면 상환·취소를 반복할 때 집계값이 어긋날 수 있다. `principalBalance`와 `feeBalance`는 스케줄에서 도출할 수 없으므로(중도상환 시 스케줄 미변경) 직접 증감시킨다.

## 5. 트랜잭션과 동시성 처리 (명세 §10)

**계좌 단위 비관적 잠금**을 선택했다.

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("SELECT a FROM LoanAccount a WHERE a.id = :id")
Optional<LoanAccount> findByIdForUpdate(@Param("id") Long id);
```

상환·전액상환·취소가 모두 이 잠금을 먼저 잡으므로 동일 계좌 요청이 한 줄로 직렬화된다. 낙관적 락 + 재시도보다 단순하고, 이 업무는 계좌 단위 처리량이 문제되지 않는다. `@Version`은 명세 §6.1이 요구해 함께 두었다(이중 안전장치).

**멱등성**은 `IDEMPOTENCY_KEY` 고유 제약으로 보장한다.

| 상황 | 동작 |
|---|---|
| 같은 키 + 같은 유형·금액 | 저장된 거래 결과를 그대로 반환 (200) |
| 같은 키 + 다른 유형·금액 | `DUPLICATE_REPAYMENT_REQUEST` (409) |
| 같은 키 동시 요청 | 고유 제약 위반을 잡아 `DUPLICATE_REPAYMENT_REQUEST` (409) |

`GlobalExceptionHandler`가 `PessimisticLockingFailureException`·`CannotAcquireLockException`·`OptimisticLockingFailureException`을 `REPAYMENT_CONCURRENCY_CONFLICT`(409)로 환원한다.

**전액상환과 일반상환의 동시 실행 방지**는 잠금 + 금액 재검증 조합으로 이루어진다. 일반상환이 먼저 커밋되면 전액상환은 재계산 금액이 달라져 `FULL_REPAYMENT_AMOUNT_CHANGED`로 거절되고, 전액상환이 먼저 커밋되면 일반상환은 `INVALID_LOAN_STATUS`(PAID_OFF)로 막힌다.

## 6. 상환 취소 및 역거래 처리 (명세 §3.7·§7.3)

원거래를 삭제하거나 금액을 수정하지 않는다. `REPAYMENT_ALLOCATION`에 **음수 금액의 역배분 행**을 추가하고 원거래는 `REVERSED`로만 바꾼다.

핵심은 **정상 반영과 취소 반영이 같은 코드를 쓴다**는 점이다.

```java
balanceApplier.apply(account, byId, schedules, lines, businessDate, +1);  // 상환
balanceApplier.apply(account, byId, schedules, lines, businessDate, -1);  // 취소
```

`sign`만 뒤집으므로 역거래가 원거래와 정확히 대칭이 된다. 비용은 `restoreFeeBalance(feeAllocated − prepaymentFee)`로 기존 잔액만 복원하고, 계좌 상태는 `accountStatusBefore`를 그대로 되돌린다.

### 취소 거절 조건

| 조건 | 에러코드 |
|---|---|
| 이미 취소된 거래 | `REPAYMENT_ALREADY_REVERSED` |
| COMPLETED가 아닌 원거래 | `REPAYMENT_REVERSAL_NOT_ALLOWED` |
| 취소 거래 자체를 취소 | `REPAYMENT_REVERSAL_NOT_ALLOWED` |
| 원거래 이후 완료된 다른 거래 존재 | `REPAYMENT_REVERSAL_NOT_ALLOWED` |
| 다른 대출계좌의 거래 | `REPAYMENT_REVERSAL_NOT_ALLOWED` |
| 환급 완료된 과오납 포함 (돈이 이미 나감) | `REPAYMENT_REVERSAL_NOT_ALLOWED` |

환급 대기·실패 상태의 과오납은 취소와 함께 `REFUND_CANCELLED`가 된다.

### 명세에 없는 보조 API (읽기 전용)

상환 결과와 잔액 정합성을 확인하기 위해 추가했다. `GET /api/loans`, `GET /api/loans/{id}`, `GET /api/loans/{id}/schedules`, `GET /api/loans/{id}/overpayments`.

**계좌 생성 API는 제공하지 않는다.** 대출 실행은 이 코어의 책임이 아니므로 `DataInitializer` 시드와 테스트 픽스처로만 적재한다.

### 전액상환 요청에 `expectedTotalAmount`를 둔 이유

명세 §7.2가 "조회한 예상금액과 실제 상환 처리 사이에 날짜가 바뀌거나 이자가 추가될 수 있으므로 처리 시점에 금액을 다시 검증한다"고 요구한다. 요청에 조회 당시 금액을 실어 보내고, 서버가 처리 시점에 재계산해 다르면 `FULL_REPAYMENT_AMOUNT_CHANGED`(409)로 거절한다.

## 8. 회계 이벤트 (명세 §11)

`ACCOUNTING_EVENT` Outbox 테이블에 상환 거래 저장과 **동일한 트랜잭션**으로 적재한다. 거래가 롤백되면 이벤트도 남지 않는다. 복식부기 분개는 명세가 허용한 대로 구현하지 않았다.

적재하는 이벤트: `LOAN_PRINCIPAL_REPAID`, `LOAN_INTEREST_RECEIVED`, `OVERDUE_INTEREST_RECEIVED`, `OVERPAYMENT_RECEIVED`, `OVERPAYMENT_REFUNDED`, `LOAN_PAID_OFF`, `REPAYMENT_REVERSED`. 취소 시에는 원거래 이벤트들을 **음수 금액**으로 적재하고 `REPAYMENT_REVERSED`를 추가한다.

### 동시성 테스트 (명세 §13.3)

명세가 요구한 5개 시나리오를 모두 작성했다.

- 동일 계좌 두 상환 동시 실행 → 2건 모두 성공, 원금 정확히 차감
- 남은 원금보다 큰 두 요청 동시 실행 → 원금 음수 안 됨, 초과분 과오납으로 분리되어 요청 총액 보존
- 동일 멱등성 키 4스레드 동시 요청 → COMPLETED 거래 **1건만** 생성, 한 번만 차감
- 전액상환 + 일반상환 동시 → 둘 다 성공하는 일이 없음
- 상환 + 상환취소 동시 → 잔액 정합성 유지

> 동시성 테스트는 클래스 레벨 `@Transactional`을 **쓰지 않는다.** 테스트 트랜잭션으로 감싸면 모든 호출이 같은 트랜잭션에 참여해 비관적 잠금 경합이 재현되지 않는다 (`bankEx`의 `TransferConcurrencyTests`와 동일한 이유).

### 정합성 검증 (명세 §13.4)

4개 불변조건을 테스트로 고정했다.

```
요청금액        = 배분금액 합계 + 과오납금액
현재 원금잔액   = 이전 원금잔액 - 원금 배분액 + 원금 취소액
스케줄 납부금액 = 해당 스케줄 배분내역 합계
원거래 배분합계 = 취소거래 역배분 합계 (부호 반대)
```

추가로 `DebtBalanceApplier`가 반영 직후 계좌·스케줄의 모든 잔액이 음수가 아닌지 검사하고, 위반 시 `REPAYMENT_ALLOCATION_FAILED`로 트랜잭션을 되돌린다.

## 12. 향후 개선이 필요한 항목

- **연체 전이 로직**이 없어 연체 시나리오를 시드로만 만들 수 있다. 실서비스에는 납부예정일 경과 시 정상→연체 버킷 이전과 연체이자 일수 계산 배치가 필요하다. 현재는 한 회차의 정상 버킷과 연체 버킷이 **상호배타적이라는 규약**을 시드가 지키는 것에 의존한다 — 코드가 강제하지 않는다.
- **중도상환수수료 산식**이 명세에 없어 계좌 단위 비율로 단순화했다. 실제로는 잔존기간·경과기간에 따라 체감하는 구조이며, 산정 대상 원금도 "배분 전 추정치"를 쓰고 있어 비용·이자가 큰 경우 실제 원금 배분액과 어긋날 수 있다.
- **과오납 환급이 2단계(요청/확정)가 아니다.** 게이트웨이 호출이 동기 성공/실패로 끝나므로 "환급 대기 → 외부 승인 → 확정" 흐름이 없다. 환급 거래의 멱등성 키도 `nanoTime` 기반이라 외부에서 재시도를 제어할 수 없다.
- **비관적 잠금은 단일 DB 전제다.** 다중 인스턴스에서도 동작하지만, 처리량이 올라가면 계좌 단위 큐잉이나 샤딩이 필요하다.
- **Outbox 소비자가 없어** 이벤트가 적재만 된다. 발행 스케줄러와 재시도·DLQ가 필요하다.
- **`Mobile/bankEx`의 기존 상환 로직과 중복**된다. 흡수하려면 `LoanApplication`에 채무 버킷(연체원금/미수이자/연체이자/비용)을 추가하고 한글 상태 문자열을 enum으로 바꿔야 하며, 전세대출 전용인 `LOAN_REPAYMENT_SCHEDULE`도 재설계가 필요하다.
- **읽기 전용 보조 API가 엔티티를 그대로 반환**한다(`GET /api/loans`가 `LoanAccount`를 직렬화). 외부 공개 전에 DTO로 감싸야 한다.
