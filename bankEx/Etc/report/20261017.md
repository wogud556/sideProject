구현 완료 리포트 (2026-10-17 — 주택담보대출, Core·Mobile 분리)

## 개요

`Etc/명세/주담대.md`를 구현했다. 저장소의 역할 구분을 따라 **업무 로직과 담당자 기능은 Core**, **고객 화면은 Mobile**에 두었다.

- `Core/mortgage/` (신규): 주담대 원장 서비스(:8084)와 담당자 화면(:5176)
- `Mobile/bankEx/`: 고객용 신청·약정·상환 화면과, Core를 호출하는 고객 채널 API. 실행금을 입금하는 내부 API도 여기에 있다

### 확정한 결정

| 항목 | 결정 | 근거 |
|---|---|---|
| Core↔Mobile 연동 | **bankEx 백엔드 → Core REST, Core → bankEx 입금 REST (양방향)** | 사용자 선택. 실제 채널→코어 구조에 맞춘다. 실행금은 bankEx 수신계좌에 들어가야 하므로 역방향 호출도 필요하다 |
| 범위 | **명세 1~8 (신청→실행) + 상환 스케줄·회차 상환** | 사용자 선택. 연체, 중도상환 수수료, 금리 변경은 제외했다 |
| 원장 위치 | 주담대 데이터는 전부 Core에 둔다 | bankEx에는 주담대 테이블을 만들지 않았다. 고객 소유 확인은 Core 응답의 customerId로 한다 |
| 영속성 | JPA만 사용 | 명세에는 MyBatis가 적혀 있다. 그러나 Core의 다른 서비스(repayment, Screening)가 JPA만 쓰므로 그쪽에 맞췄다 |
| 프로젝트 간 호출 | 이번이 **처음으로 생긴 백엔드 간 의존**이다 | 저장소 원칙("서로 호출하지 않는다")의 예외다. CLAUDE.md에 반영했다 |

## 1. 업무 흐름과 역할 분담

```
[고객 · bankEx 앱]        [bankEx :8080]                 [Core/mortgage :8084]           [담당자 :5176]
 신청 ───────────────▶ 회원 확인 ──── POST /applications ──▶ APPLIED
                                                            COLLATERAL_EVALUATED ◀──── 담보 평가 (OPS)
                                                            LIMIT_CALCULATED     ◀──── 한도 산정 (UW)
                                                            심사 결과 4종         ◀──── 여신 심사 (UW)
                                                            APPROVED             ◀──── 대출 승인 (AP)
 약정 ───────────────▶ 입금계좌 소유 확인 ── /agreements ─▶ AGREED
                                                            EXECUTION_READY      ◀──── 근저당 설정·조건 이행 확인 (OPS)
                       /api/internal/... 입금 ◀──────────── EXECUTED             ◀──── 대출 실행 (OPS)
 상환 ───────────────▶ 출금 ─────────── /repayments ──────▶ 회차 납부
```

담당자 역할은 3개다. 한 담당자는 역할 하나만 가지므로 **심사자와 승인자가 자연히 분리**된다.

| 역할 | ID(시드) | 업무 |
|---|---|---|
| OPERATIONS 여신 실무 | OPS01 | 담보 평가, 근저당 설정·조건 이행 확인, 대출 실행 |
| UNDERWRITER 심사역 | UW01 | 한도 산정, 여신 심사 |
| APPROVER 승인권자 | AP01 | 대출 승인, 규제 정책 등록 |

인증은 없다. Core/refinancing과 같은 방식으로 `X-Operator-Id` 헤더만 받고 역할을 확인한다.

### 상태 전이 (`ApplicationStatusTransition`)

```
APPLIED → COLLATERAL_EVALUATED → LIMIT_CALCULATED → { SCREENING_APPROVED | CONDITIONALLY_APPROVED | DOCUMENT_REQUIRED | REJECTED }
SCREENING_APPROVED / CONDITIONALLY_APPROVED → APPROVED → AGREED → EXECUTION_READY → EXECUTED
실행 전 모든 단계 → WITHDRAWN (고객 철회)
```

- 담보를 재평가하면 상태가 COLLATERAL_EVALUATED로 돌아간다. 한도를 다시 산정해야 심사할 수 있다.
- DOCUMENT_REQUIRED에서는 재심사, 한도 재산정, 담보 재평가를 할 수 있다.
- 명세 1의 원칙대로 **심사 승인 ≠ 대출 승인 ≠ 실행 가능**이다. 조건부 승인 건은 승인과 약정을 마쳐도, 담당자가 조건 이행을 확인해야 EXECUTION_READY가 된다.

## 2. Core/mortgage 백엔드

패키지 `com.hanati.bank.mortgage`. 명세 2의 모듈 구성을 따랐다.

| 모듈 | 내용 |
|---|---|
| `application/` | 신청 원장, 담보 주택, 소득, 기존 부채. 상태 전이 규칙 |
| `collateral/` | 평가 이력(`MORTGAGE_VALUATION`), 권리관계(`MORTGAGE_LIEN`: 선순위 근저당·임차보증금·당행 근저당) |
| `policy/` | 규제 정책 테이블과 `PolicyResolver` |
| `limit/` | 한도 산정 엔진과 결과(`MORTGAGE_LIMIT_RESULT`) |
| `screening/` | 심사 엔진과 이력(`MORTGAGE_SCREENING`) |
| `approval/` | 승인(`MORTGAGE_APPROVAL`), 약정(`MORTGAGE_AGREEMENT`), 실행 선행조건 |
| `execution/` | 실행 이력(`MORTGAGE_EXECUTION`), 대출 계좌(`MORTGAGE_LOAN_ACCOUNT`) |
| `repayment/` | 상환 계산기 3종, 예정표, 상환 거래 |
| `gateway/` | `DisbursementGateway` — bankEx 구현과 Mock 구현 |
| `operator/`, `product/` | 담당자와 역할, 상품 2종 |

명세 3의 테이블 13개를 모두 만들었다. 추가로 `MORTGAGE_POLICY`, `MORTGAGE_PRODUCT`, `MORTGAGE_OPERATOR`, `MORTGAGE_LOAN_ACCOUNT`를 두었다. `MORTGAGE_LOAN_ACCOUNT`는 명세의 "공통 여신계좌"를 대신한다. 그런 테이블이 저장소에 없기 때문이다.

### 2.1 한도 산정 엔진 (명세 4)

```
LTV 한도     = 평가액 × LTV
담보가용액   = LTV 한도 − 선순위 채권·임차보증금            (명세의 CollateralLimitCalculator)
DTI 한도     = (연소득 × DTI − 기존 주담대 원리금 − 기타 부채 이자) 를 원금으로 역산   (신DTI)
DSR 한도     = (연소득 × DSR − 기존 부채 원리금) 를 원금으로 역산
스트레스 DSR = DSR 한도를 (적용금리 + 가산금리)로 다시 역산
최종 한도    = min(담보가용액, DTI, 스트레스 DSR, 상품 한도, 규제 최대 금액)
```

- 역산 방식: 상환액은 원금에 비례하므로 "원금 1원당 연간 원리금(factor)"을 먼저 구하고 `여력 ÷ factor`로 원금을 낸다(`AnnualDebtService`). 상환 방식 세 가지 모두 첫 1년 기준이다. 만기일시는 원금을 대출기간으로 나눠 매년 갚는 것으로 본다.
- 한도는 만원 미만을 버린다. 최종 한도를 결정한 제약(`bindingConstraint`)도 함께 저장한다.
- 명세 예시(5억·LTV 70%·연소득 6,500만·4%·30년)를 넣으면 LTV 한도 3억 5천만 원이 최종 한도로 나온다. 테스트로 고정했다.
- 명세의 Ltv/Dti/Dsr/StressDsr Calculator를 각각 클래스로 만들지 않고 엔진 메서드 안에서 계산했다. 계산마다 한두 줄이라 클래스로 나눌 이유가 없었다.

### 2.2 규제 정책 엔진 (명세 5)

- `MORTGAGE_POLICY`: 유형(LTV·DTI·DSR·STRESS_RATE·MAX_LOAN_AMOUNT), 지역, 차주 유형, 상품, 값, 적용기간, 버전, 근거. 조건 컬럼의 `ALL`은 와일드카드다.
- 선택 규칙: 기준일에 유효한 후보 중 **상품(4) > 차주 유형(2) > 지역(1)** 가중치 합이 가장 큰 행을 고른다. 합이 같으면 버전이 높은 행이다. 예를 들어 규제지역의 생애최초 구입자에게는 LTV 80%(생애최초)가 50%(규제지역)보다 우선한다.
- 정책 행은 수정하지 않는다. 새 버전을 등록하면 같은 조건의 이전 버전은 시작일 전날로 닫힌다.
- 한도 산정 결과에 **적용한 정책 ID 5개와 입력값·산출값을 모두 저장**한다. 그래서 정책이 바뀐 뒤에도 당시 결과를 재현할 수 있다.
- 시드: 스트레스 가산금리를 2026-07-01 기준으로 v1(0.75%p)과 v2(1.50%p)로 나눠 버전 관리를 보여 준다. **정책 값은 학습용 예시이며, 실제 감독규정 수치와 다를 수 있다.**

### 2.3 심사 엔진 (명세 6)

한도 엔진과 분리했다(명세 10의 둘째 원칙). 영역별로 PASS·HOLD·FAIL을 판정한 뒤 종합한다.

| 영역 | FAIL | HOLD |
|---|---|---|
| 차주 | 신용점수 < 600 | 소득 증빙 미확인 |
| 담보 | 담보가용액 0 | 소유권·등기 서류 미확인 |
| 규제 | 최종 한도 0 | 신청 금액 > 최종 한도 (한도 내 감액) |

종합 판정 순서는 다음과 같다. FAIL이 하나라도 있으면 거절이다. 그다음 소득 증빙이 없으면 추가 서류 요청이다. 그 외에 HOLD가 있으면 조건부 승인이고, 나머지는 승인이다. 소유권 서류 HOLD가 있으면 승인에 "실행 전 조건 이행 확인"이 붙는다.

명세의 `PENDING`·`IN_PROGRESS`는 두지 않았다. 심사는 요청 즉시 끝나기 때문이다.

### 2.4 승인·약정·실행 (명세 7)

- 승인: 금리는 심사 근거였던 한도 산정의 적용 금리(상품 기준금리 + 신용점수 가산)로 확정한다. 승인 금액은 상품 최소 금액 이상, 심사 권고 금액 이하여야 한다. 승인 유효기간은 30일이다.
- 약정: 고객이 bankEx에서 동의하고 실행금 입금 계좌를 고른다. 계좌가 본인 소유의 정상 계좌인지는 bankEx가 확인한다.
- 선행조건: 당행 근저당을 등록한다(채권최고액 = 대출금 × 120%). 조건부 승인 건은 조건 이행도 확인해야 한다.
- 실행 정합성
  - 신청 행에 비관적 잠금을 건다.
  - `Idempotency-Key` 헤더를 받는다. 같은 키로 다시 요청하면 처음 결과를 돌려준다.
  - **bankEx 입금 키는 신청 건마다 `MGD-{신청번호}` 하나로 고정**한다. 입금된 뒤 Core 트랜잭션이 롤백되어 다시 실행하더라도 입금은 한 번뿐이다.
  - 입금이 실패하면 FAILED 이력을 남기고 EXECUTION_READY를 유지한다. 새 키로 재시도하면 된다.
- 실행에 성공하면 대출 계좌를 만들고 상환 예정표를 생성한다(납기일 = 실행일 + n개월, 휴일 조정은 없다).

### 2.5 상환 (명세 7)

- `RepaymentCalculator` 인터페이스와 구현 3개(원리금균등, 원금균등, 만기일시). 원금 끝전은 마지막 회차가 흡수한다.
- 회차 상환: 다음 미납 회차 한 건을 청구액 그대로 납부하는 것만 지원한다. bankEx의 출금 거래번호를 멱등 키로 받는다. 마지막 회차를 내면 계좌가 완제(CLOSED)된다.

## 3. Mobile/bankEx 변경

### 백엔드 — `loan/mortgage/` (신규)

- `MortgageCoreClient`: Core 고객용 API만 호출한다. Core의 업무 오류는 `MortgageCoreException`으로 받아 Core의 코드와 메시지를 그대로 고객에게 전달한다. 연결이 실패하면 `MORTGAGE_CORE_UNAVAILABLE`을 던진다.
- 고객 API (`/api/bank/user/loan/mortgage`): 상품 조회, 신청, 내 신청 목록·상세, 약정, 철회, 대출 계좌·스케줄 조회, 회차 상환.
  - 고객에게는 한도 산정 근거, 심사 사유, 담당자 정보를 내보내지 않는다. 상태별 안내 문구(`notice`)만 준다.
  - **상환**: 출금(`debitLocked`)과 Core 반영을 한 로컬 트랜잭션으로 묶는다. Core가 거절하거나 연결이 끊기면 출금도 롤백된다.
- 내부 API `POST /api/internal/mortgage/disbursements`: Core만 호출하는 실행금 입금 API다. 공유 토큰(`X-Internal-Token`)을 확인한다. 멱등 키를 `DEPOSIT_TRANSACTION.TRANSACTION_NUMBER`(unique)로 그대로 쓰고, 계좌 잠금을 잡은 뒤 키를 확인한다.
- 기존 파일 수정은 최소로 했다: `ErrorCode` 4개 추가, `GlobalExceptionHandler`에 `MortgageCoreException` 처리 추가, `DepositTransactionRepository.findByTransactionNumber` 추가, `application.yml`에 Core 주소와 토큰 추가.

### 프론트 — 3페이지

- `MortgageApply`: 상품 선택 후 신청서 작성(대출 조건, 담보 주택, 소득, 기존 대출)
- `MortgageApplications`: 신청 목록·상세, 승인 조건 확인, 약정(입금 계좌 선택, 동의), 철회, 대출 계좌 목록
- `MortgageAccount`: 대출 잔액, 이번 회차 상환(출금 계좌 선택), 상환 스케줄
- 홈에 "주택담보대출"과 "내 주담대" 메뉴를 추가했다.
- 명세의 Zustand·Zod는 쓰지 않았다. bankEx 프론트의 기존 방식(localStorage 사용자, 화면별 useState)에 맞췄다.

## 4. Core/mortgage 담당자 화면 (:5176)

- `ApplicationQueue`: 단계별 업무 대기 탭(담보 평가 대기, 한도 산정 대기, 심사 대기, 추가 서류, 승인 대기, 조건부 승인 대기, 선행조건 확인, 실행 대기, 전체). 탭마다 처리 역할을 표시한다.
- `ApplicationDetail`: 신청 정보와 단계별 패널 5개(담보, 한도, 심사, 승인·약정·선행조건, 실행). 현재 단계의 패널에만 처리 폼이 나온다. 한도 패널은 제약별 한도와 근거를 보여 주고, 최종 한도를 결정한 제약을 강조한다.
- `PolicyList`: 정책 목록(유효기간이 지난 행은 흐리게)과 새 버전 등록
- `LoanAccountDetail`: 대출 계좌, 상환 거래, 상환 스케줄
- 헤더에서 담당자를 고른다(`operatorStore`, Zustand persist). Axios 인터셉터가 `X-Operator-Id`를 붙인다.
- 실행 버튼은 `crypto.randomUUID()`로 만든 키를 쓴다. 응답을 받지 못해 다시 눌러도 같은 키를 보내고, FAILED 응답을 받으면 새 키로 바꾼다.

시드: 담당자 3명, 상품 2종, 정책 11행, 시연 신청 3건(담보 평가 대기, 심사 대기, 조건부 승인 대기). 시연 고객 demo01~03은 bankEx에 없는 고객이라 약정 이후로는 진행할 수 없다.

## 6. 범위에서 제외한 것 · 알려진 한계

- **명세 9단계(사후 관리)**: 연체 전이와 연체이자, 중도상환과 수수료, 금리 변경, 부분상환, 휴일 조정, 일할 이자. Core/repayment에 배분·역분개 로직이 있지만 연결하지 않았다.
- **상환의 응답 유실 구간**: Core가 상환을 커밋했는데 응답이 bankEx에 도착하기 전에 끊기면, bankEx는 출금을 롤백하고 Core에는 상환이 남는다. 실행 쪽은 입금 키를 고정해서 막았지만, 상환 쪽에는 대사(reconciliation)나 출금 선확정 후 재전송 같은 장치가 더 필요하다.
- **실행 중 외부 호출**: 실행 트랜잭션이 신청 행 잠금을 잡은 채로 bankEx를 호출한다. 학습용 규모에서는 문제없지만, 운영이라면 실행 요청을 먼저 커밋하고 비동기로 처리하는 편이 낫다.
- **인증**: 담당자는 헤더, 고객은 `userId` 파라미터만 쓴다(bankEx 기존 방식). 내부 API는 공유 토큰뿐이다.
- **bankEx 계좌 해지 검사**: `ACCOUNT_HAS_ACTIVE_LOAN` 검사는 bankEx 일반대출만 본다. 주담대 실행금 입금 계좌를 해지해도 막지 못한다.
- **신용점수**: 신용평가사 연동 없이 심사역이 한도 산정 때 입력한다.
- **동시 결정 경합**은 신청 행 비관적 잠금으로 막았다. 다만 H2 기준으로만 확인했다.

## 7. 실행 방법

두 백엔드를 함께 띄워야 고객 신청부터 실행까지 이어진다. 한쪽만 띄워도 기동은 되지만, 상대 서버를 호출하는 요청은 실패한다.

```bash
# 백엔드
cd Core/mortgage/backend/mortgage && ./gradlew bootRun        # :8084
cd Mobile/bankEx/backend/bankEx && ./gradlew bootRun          # :8080

# 프론트
cd Core/mortgage/front/mortgage_front && npm install && npm run dev   # 담당자 :5176
cd Mobile/bankEx/front/bankEx_Front && npm run dev                    # 고객 :5173
```

시연 순서:

1. bankEx에서 회원가입하고 계좌에 입금한다.
2. 홈 → "주택담보대출"에서 신청한다.
3. 담당자 화면에서 단계별로 처리한다. 화면 헤더에서 담당자를 바꿔 가며 진행한다.
   - OPS01: 담보 평가
   - UW01: 한도 산정, 심사
   - AP01: 승인
4. bankEx "내 주담대"에서 약정한다.
5. 담당자 화면에서 OPS01로 선행조건을 확인하고 대출을 실행한다.
6. bankEx 계좌 잔액이 늘었는지 확인한 뒤, "대출 계좌 · 상환 보기"에서 1회차를 상환한다.

Core만 단독으로 띄우려면 `mortgage.gateway.mode=mock`으로 설정한다. 실행금 입금이 bankEx 대신 Mock으로 처리된다.
