## 개요

`명세/대환.md`(가계대출 대환 업무 시스템 개발 명세서, 39개 섹션)에 따라 은행의 가계대출 대환(대환대출) 업무 시스템을 신규 개발했다. 명세 39번의 지시("이미 존재하는 구조를 무시하고 새 프로젝트를 임의로 만들지 않는다")에 따라 개발 착수 전 `bankEx/`, `Screening/` 두 기존 프로젝트의 패키지 구조·예외처리·응답 포맷·ID 채번 방식·테스트 스타일·프론트 컨벤션을 먼저 조사했고, 그 결과를 최대한 재사용했다.

사용자와 사전에 두 가지를 확정하고 시작했다.

1. **프로젝트 위치**: 저장소 루트에 `대환/backend/refinance` + `대환/front/refinance_front`로 완전 독립 프로젝트를 새로 만들되(= `Screening/`과 동일한 선례), `bankEx/` 기존 코드는 건드리지 않고 나중에 필요 시 패키지 단위로 흡수한다.
2. **권한관리(명세 31번) 스코프**: 실제 Spring Security 인증(로그인/세션/JWT)이 아닌, 직원 테이블 + `X-Operator-Id` 헤더 기반 경량 역할 검증으로 구현 범위를 의도적으로 축소한다(README에 명시, 추후 bankEx 흡수 시 JWT로 교체 필요).

명세 36번이 제시한 Phase 1~10 순서를 그대로 따라, 각 Phase 경계마다 `./gradlew compileJava` 또는 `test`, 프론트는 `tsc -b`로 컴파일 확인 후 다음 단계로 진행했다.

## 핵심 설계

### 상태 머신

```
DRAFT → REQUESTED → REVIEWING → (APPROVED | REJECTED) → EXECUTING → NEW_LOAN_EXECUTED → REPAYING → COMPLETED
                                                              ↓                              ↓
                                                            FAILED ───────────────────────────┘
```

`RefinanceStatusTransition`이 `Map<RefinanceStatus, Set<RefinanceStatus>>`로 허용 전이만 화이트리스트로 관리하며, `RefinanceApplication.changeStatus()`가 매 전이마다 검증 후 위반 시 `INVALID_APPLICATION_STATUS` 예외를 던진다. `FAILED`에서의 재처리는 `TB_REFINANCE_ERROR.failedStep`을 보고 `EXECUTING`(신규대출 미실행) 또는 `REPAYING`(신규대출 이미 실행됨, 상환만 재시도)으로만 분기하도록 전이 맵 자체에서 `FAILED → NEW_LOAN_EXECUTED`, `FAILED → COMPLETED` 등의 건너뛰기를 원천 차단했다.

### 거래정합성 / 중복 실행 방지 (명세 17·18·22번)

- `RefinanceExecutionService.execute()`는 먼저 `updateStatusIfMatch(APPROVED → EXECUTING)` 상태조건부 UPDATE를 시도하고, 영향받은 row가 0이면 이미 다른 요청이 실행 중/완료된 것으로 보고 `CONCURRENT_MODIFICATION`을 던진다 — 이 문(門) 하나로 "두 번 실행 요청해도 실제 금융거래는 한 번만" 요구사항을 만족시킨다.
- 신규대출 실행 단계(`executeNewLoanStep`)와 기존대출 상환 단계(`repayExistingLoansStep`)를 별도 메서드로 분리해, 재처리 시 `failedStep=EXISTING_LOAN_REPAYMENT`인 경우 상환 단계만 재호출하고 신규대출 실행 메서드는 절대 다시 호출하지 않는다.
- `RefinanceApplication`에 `@Version`(낙관적 락)을 적용했다 — bankEx/Screening 어느 프로젝트에도 없던 신규 도입.
- `TB_REFINANCE_TRANSACTION.REQUEST_ID`에 UNIQUE 제약을 걸어 거래고유번호 중복을 DB 레벨에서도 방어한다.

### Gateway / Mock (명세 15·16번)

```java
public interface LoanExecutionGateway { LoanExecutionResult executeLoan(LoanExecutionRequest request); }
public interface LoanRepaymentGateway {
    RepaymentInquiryResult inquireRepaymentAmount(RepaymentInquiryRequest request);
    RepaymentResult repay(RepaymentRequest request);
}
```

`MockLoanExecutionGateway`/`MockLoanRepaymentGateway`가 `DemoScenarioAccounts`에 정의된 특정 계좌번호를 참조해 실패 시나리오를 **결정적으로** 재현한다. 특히 `MockLoanRepaymentGateway`는 계좌별 시도 횟수를 기억해 최초 1회만 실패하고 재처리 시 성공하도록 구현해, 명세 34번이 요구하는 "신규대출 성공 + 상환 실패 → 재처리 → 성공" 시나리오를 테스트로 결정적으로 검증할 수 있게 했다.

### DB 설계 (명세 23번, 총 11개 테이블)

`TB_CUSTOMER`, `TB_LOAN`, `TB_REFINANCE_OPERATOR`(경량 권한용 추가), `TB_REFINANCE_APPLICATION`, `TB_REFINANCE_TARGET`, `TB_REFINANCE_REVIEW`, `TB_REFINANCE_APPROVAL`, `TB_REFINANCE_TRANSACTION`, `TB_REFINANCE_HISTORY`, `TB_REFINANCE_ERROR`, `TB_AUDIT_LOG`.

- 로컬/테스트: `spring.jpa.hibernate.ddl-auto=create-drop`으로 H2에 엔티티 기반 자동 생성 (Screening 컨벤션).
- 운영: `src/main/resources/oracle-ddl.sql`에 PK/FK/UNIQUE/INDEX 포함 Oracle DDL을 수동 작성 (bankEx `migration/*.sql` 컨벤션 — 자동 실행되지 않음, 수동 반영 필요).

### API / 화면

명세 25번 REST API 목록(고객·기존대출 조회, 대환가능여부, 상환금액조회, 신청/심사/승인/거절/실행/재처리/이력)을 컨트롤러별로 그대로 구현했고, `PUT /applications/{id}`(신청수정)만 이번 스코프에서 제외했다. 프론트는 명세 28번 화면 8개(Dashboard, 고객검색, 고객대출현황, 7-STEP 대환신청 위저드, 심사, 실행, 실패거래/재처리, 업무이력)를 전부 구현했고, 경량 권한모델을 위해 명세에 없는 "직원 선택" 화면 1개를 추가했다.

## 작업 중 발견하고 수정한 실제 버그 3건

curl로 각 Phase를 실제 구동하며 검증하는 과정에서 발견했다.

| 증상 | 원인 | 수정 |
|---|---|---|
| `GET /api/refinance/errors` 호출 시 500 (`Invalid bound statement`) | `application-local.yml`에서 `mybatis:` 키를 `spring:` 하위에 잘못 중첩(Screening의 기존 yml을 그대로 복사했는데, Screening은 MyBatis 매퍼 XML을 실제로 쓰지 않아 이 오류가 지금까지 드러난 적이 없었음) | `mybatis:`를 최상위 키로 이동 (bankEx `application.yml` 컨벤션과 동일하게) |
| `execute()`가 상태를 정상적으로 `APPROVED → EXECUTING`으로 바꿨는데도 바로 다음 줄에서 `INVALID_APPLICATION_STATUS` 예외 발생 | 같은 트랜잭션 안에서 JPQL 벌크 `@Modifying` UPDATE(`updateStatusIfMatch`) 실행 후, 이미 영속성 컨텍스트에 캐시된 엔티티를 `findById`로 재조회하면 Hibernate 1차 캐시가 갱신되지 않아 stale 상태를 반환하는 전형적인 함정 | `@Modifying(clearAutomatically = true, flushAutomatically = true)` 추가 |
| 심사(`review()`) 처리 시 항상 "부적격"으로 판정 | 대환가능여부 재검증 로직(`ALREADY_IN_PROGRESS`)이 진행 중인 신청 목록을 조회할 때 **현재 심사 중인 신청 자기 자신**을 걸러내지 않아 항상 "이미 진행 중인 신청 존재"로 오판 | `RefinanceEligibilityService.check()`에 `excludeApplicationId` 파라미터를 추가해 심사 단계에서는 자기 자신을 제외하도록 오버로드 |

세 버그 모두 실제 HTTP 요청을 여러 시나리오(정상/연체/잔액없음/실행실패/상환실패)로 구동해보다가 발견했고, 재현 → 원인 파악 → 수정 → 재검증까지 마쳤다.
