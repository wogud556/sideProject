구현 완료 리포트 (2026-10-11 — Screening 심사역용 전환)

## 개요

`Etc/명세/기타구현해야하는_2.md` §9 "Screening 프로젝트 정리"를 진행했다. 출발점은 저장소의 역할 구분이다. **Mobile은 고객용 채널이고, Core는 은행 담당자가 쓰는 관리 기능과 업무 로직**을 맡는다. 그런데 `Core/Screening`은 회원가입부터 대출 신청까지 처리하는 고객용 앱이었다.

§9.2에 따라 먼저 분석 보고서를 내고 사용자 확인을 받았다. 그 뒤 고객 기능을 걷어내고 **심사역용 심사 서비스**로 바꿨다.

### 확정한 결정

| 항목 | 결정 | 근거 |
|---|---|---|
| §9.5 처리 방안 | **B(별도 서비스 유지)의 변형** | Core는 담당자용이라는 역할 구분. 심사 엔진은 재사용할 가치가 있고, 고객 기능은 bankEx와 중복된다 |
| bankEx 연동 | **이번 범위에서 제외 (1안)** | 저장소 원칙이 "프로젝트 간 호출 없음"이다. 먼저 Core 안에서 끝낼 수 있는 범위만 했다 |
| 심사 규칙 | **§9.4를 따르고, 기존 엔진의 700점 기준은 수동심사로 살림** | 기존 CONDITIONAL(70% 자동 감액)을 §9.3의 MANUAL_REVIEW로 대체했다 |

## 1. 착수 전 분석 결과 (§9.2)

### Screening 현황

| 구분 | 내용 | 판정 |
|---|---|---|
| 회원 (`UserInfo`, 가입·로그인·프로필) | 고객용 | 폐기 |
| 상품 (`LoanProduct`) | bankEx 상품과 중복 | 폐기 |
| 신청 (`LoanApplication`, 내 신청 목록) | 고객용 | 폐기 |
| 심사 엔진 (`LoanScreeningEngine`, CSS·DSR) | 재사용 가치 있음 | 유지하되 §9.4 규칙으로 재작성 |
| 프론트 8페이지, 스토어 4개 | 전부 고객용 | 폐기 |

### 발견한 결함 (개편 전)

- **신용정보 등록 API가 없었다.** 시드 데이터의 `test01`만 심사할 수 있었고, 새로 가입한 고객은 심사 요청이 항상 실패했다.
- **같은 신청을 여러 번 심사할 수 있었다.** 결과가 2건 이상 쌓이면 `findByApplicationId`(단건 조회)가 예외를 던져 결과 조회가 500으로 실패했다.
- `@RestControllerAdvice`가 없어서 `IllegalArgumentException`이 500으로 나갔다.
- 금액과 비율을 `double`로 계산했다. 연소득이 0이면 DSR이 무한대가 되어 `BigDecimal.valueOf`에서 예외가 났다.
- `existingDebt`와 상품 최대 한도는 심사에 쓰이지 않았다.

### bankEx 심사 로직과의 중복 (§9.2-2~4)

| 조건 | 기존 Screening | 전세대출 | 일반대출 |
|---|---|---|---|
| 신용점수 거절 | <700 | <600 (SGI <700) | 심사 없음 |
| 부채 기준 | DSR >50% | 부채/소득 ≥70% (SGI ≥50%) | 심사 없음 |
| 한도 | 상품 한도 무시 | min(보증금 80%, 소득×3.5−부채, 상품 한도) | 상품 한도만 확인 |

일반대출의 `approveApplication`은 상태 문자열을 "승인"으로 바꾸기만 한다. 전세대출의 보증기관 심사와 계약 검증은 전세에만 해당하는 규칙이어서 bankEx에 그대로 둔다.

## 2. 구현 내용

### API (`/api/screenings`)

| 메서드 | 경로 | 설명 |
|---|---|---|
| POST | `/loans` | 심사 실행. 요청 필드는 §9.3 기준 |
| GET | `/?status=` | 목록. 상태를 지정하면 접수순, 생략하면 최신순 |
| GET | `/{screeningId}` | 상세 |
| POST | `/{screeningId}/approve` | 심사역 승인. `approvedAmount`를 생략하면 전액 승인, 지정하면 감액 승인 |
| POST | `/{screeningId}/reject` | 심사역 거절 |

### 심사 규칙 (`LoanScreeningEngine`, 위에서부터 평가)

1. 신용점수 < 600 → 거절 `LOW_CREDIT_SCORE`
2. 기존대출 + 신청액 > 연소득 × 10 → 거절 `DEBT_LIMIT_EXCEEDED`
3. 신청액 > 연소득 × 5 (500%) → 수동심사 `INCOME_MULTIPLE_EXCEEDED`
4. 신용점수 600~699 → 수동심사 `BORDERLINE_CREDIT_SCORE`
5. 그 외 → 승인. 금리는 신용점수 구간별(≥900 3.50 / ≥800 4.20 / ≥700 5.50 / 그 외 7.00)

거절 규칙을 수동심사 규칙보다 먼저 평가한다. §9.4는 "내부 기준"의 값을 정하지 않아서 10배로 정했다. 연소득이 0원이면 2번 규칙에서 거절되며, 0으로 나누는 계산은 없다.

### 구조

- 엔티티는 `LoanScreening` 하나다. 요청, 결과, 심사역 결정을 한 행에 담는다.
- 고객 정보는 테이블 없이 요청 본문으로 받는다. 개편 전 "신용정보 미등록" 결함은 이 방식으로 없어졌다.
- 결정은 `MANUAL_REVIEW` 상태에서만 가능하다. 이중 결정을 막는다.
- 예외 처리는 bankEx 패턴(`BusinessException` + `ErrorCode` + `GlobalExceptionHandler`, 전부 400)을 따른다. `@Valid` 실패도 `INVALID_REQUEST`로 응답한다.
- `DataInitializer`는 규칙별 결과가 하나씩 나오도록 5건을 시드한다(승인 1, 거절 2, 수동심사 2).
- `spring-security-crypto` 의존성과 `SecurityConfig`를 제거했다. 비밀번호를 다루는 곳이 더 이상 없다.

### 프론트 (3페이지)

- `ScreeningQueue`: 상태 탭(기본값 "수동심사 대기"), 심사역 ID 입력, 목록
- `ScreeningDetail`: 요청 내용, 결과, 심사역 결정 이력. 수동심사 건에는 승인(감액 가능)과 거절 폼이 나온다.
- `NewScreening`: bankEx 연동 전까지 심사 요청을 직접 넣는 화면
- `reviewerStore`: 심사역 ID 보관(Zustand persist). 인증은 없다.

## 4. 범위에서 제외한 것

- **bankEx 연동 (2안).** bankEx 일반대출 신청이 `POST /api/screenings/loans`를 호출하게 하는 작업이다. 프로젝트 간 첫 의존이 생기므로 따로 결정한다.
- **bankEx 안에 있는 담당자 기능.** `/loan/applications/{id}/approve`, `/loan/disbursement`, 전세대출 `review`/`execute`, 스케줄러 엔드포인트가 고객 경로(`/api/bank/user`) 아래에 있다. 연동할 때 함께 정리한다.
- **동시 결정 경합.** 두 심사역이 같은 건을 동시에 결정하면, 상태 검사만으로는 막지 못하고 마지막 커밋이 이긴다. 필요하면 `@Version` 낙관적 락을 추가한다.
- **실제 인증과 심사역 권한 모델.**
- **HTTP 상태 세분화.** 404와 409 대신 bankEx처럼 전부 400으로 응답한다.
