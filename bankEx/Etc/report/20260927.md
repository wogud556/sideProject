## 개요

`명세/기타구현해야하는_2.md` 섹션 4(정기예금 업무)에 따라 bankEx에 정기예금 도메인을 신규 추가했다. 기존에는 매월 납입하는 적금(`deposit/savings`)만 있었고, 목돈을 한 번에 예치해 만기에 원리금을 받는 상품이 없었다.

개발 착수 전 가장 유사한 기존 도메인인 `deposit/savings`의 전체 구현(컨트롤러·서비스 7개·MyBatis 매퍼·이자 계산·시드데이터·테스트)과 `deposit/general`의 입출금 처리(`transService`)를 먼저 읽고, 패키지 구조·예외처리·채번·테스트 스타일을 그대로 따랐다.

명세 §2.1이 정한 구현 범위(엔티티/DB, Mapper, Service, Controller, DTO, 핵심 로직, 최소 단위 테스트)에 맞춰 **백엔드만** 구현했다. 적금도 프론트 화면이 없으므로(`pages/deposit/savings/.gitkeep`) 동일한 선례를 따랐다.

착수 전 사용자와 두 가지를 확정했다.

1. **이자소득세 15.4% 적용**. 명세 4.5는 단리 공식만 정의하고 세금을 언급하지 않지만, 같은 수신 도메인인 적금이 `savingsInterestService.calculateTax()`로 15.4%를 차감하고 있어 일관성을 맞췄다.
2. **만기 배치 엔드포인트 추가**. 명세는 상태값 4개(ACTIVE/MATURED/TERMINATED/CANCELLED)를 주면서 API는 `terminate` 하나만 정의한다. 적금의 `/scheduler/maturity` 패턴을 따라 6번째 API를 추가하고, 만기는 배치가 `MATURED`로, 중도해지는 `terminate`가 `TERMINATED`로 처리하도록 역할을 분리했다.

## 핵심 계산 로직

명세 4.5의 단리 공식을 `FixedDepositInterestCalculator` 한 곳에 모았다. 만기와 중도해지가 같은 공식을 쓰고 **금리와 개월 수만 달라진다**는 점을 이용해 메서드 하나로 통합했다.

```java
// 단리 이자 = 예치 원금 × 연 이자율 × 개월 수 / 12
public long calculateInterest(long principalAmount, double annualRatePercent, int months) {
    return Math.round(principalAmount * (annualRatePercent / 100) * months / 12.0);
}

public long calculateTax(long interest) {
    return Math.round(interest * 0.154);
}

// 예치 시작일부터 해지일까지 경과한 온전한 개월 수
public int elapsedMonths(LocalDate startDate, LocalDate terminationDate) {
    return (int) ChronoUnit.MONTHS.between(startDate, terminationDate);
}
```

| 구분 | 금리 | 개월 수 |
|---|---|---|
| 만기 | `product.interestRate` (3.5%) | `product.termMonths` (12) |
| 중도해지 | `product.earlyTerminationRate` (0.5%) | `elapsedMonths(startDate, today)` |

적금은 회차별 납입액마다 잔여개월을 따로 곱해 합산해야 하지만(`savingsInterestService.calculateInterest`), 정기예금은 원금이 한 번에 예치되므로 훨씬 단순하다. 적금의 `earlyTerminationRateRatio`(경과율 구간별 30%/50%/80% 차등)도 쓰지 않는다 — 명세가 `earlyTerminationRate`를 **상품의 절대 금리**로 정의하기 때문이다.

### 예상 만기금액의 저장 시점

`expectedInterest`와 `expectedMaturityAmount`는 가입 시점에 계산해 `FIXED_DEPOSIT_ACCOUNT`에 저장한다. 정기예금은 금리와 기간이 가입 시점에 확정되므로 만기 지급액도 그때 확정된다.

- `expectedInterest` = **세전** 이자 (350,000)
- `expectedMaturityAmount` = 원금 + 이자 − 세금 = **세후 실지급 예상액** (10,296,100)

만기 배치는 저장된 `expectedInterest`를 그대로 지급하므로, 가입 시 안내한 금액과 실제 지급액이 항상 일치한다.

## 주요 업무 흐름

명세 4.2의 흐름을 그대로 따랐다.

### 가입 (`POST /fixed-deposits`)

```
1. 요청 필수값 검증           → INVALID_REQUEST / INVALID_AMOUNT
2. 고객 조회 + ACTIVE 확인     → CUSTOMER_NOT_FOUND / CUSTOMER_NOT_ACTIVE
3. 출금계좌 조회 + ACTIVE 확인  → ACCOUNT_NOT_FOUND / ACCOUNT_NOT_ACTIVE
4. 출금계좌 잔액 확인          → INSUFFICIENT_BALANCE
5. 상품 조회 + ON_SALE 확인    → FIXED_DEPOSIT_PRODUCT_NOT_FOUND / _PRODUCT_CLOSED
6. 예치금액 범위 확인          → FIXED_DEPOSIT_AMOUNT_OUT_OF_RANGE
7. 가입기간 == 상품기간 확인    → FIXED_DEPOSIT_INVALID_TERM
8. 만기 예상금액 계산
9. transService.debit()로 원금 출금   (거래내역 FIXED_DEPOSIT_SUBSCRIBE)
10. 계좌번호 채번 + 계좌 생성 (ACTIVE)
```

출금과 계좌 생성은 `@Transactional` 하나로 묶여 있어, 계좌 생성이 실패하면 출금도 롤백된다.

### 중도해지 (`POST /{id}/terminate`)

```
1. 계좌 조회                        → FIXED_DEPOSIT_ACCOUNT_NOT_FOUND
2. 상태 == ACTIVE 확인               → FIXED_DEPOSIT_ALREADY_TERMINATED
3. 기준일 < 만기일 확인               → FIXED_DEPOSIT_MATURITY_REACHED
4. 경과 개월 수 × earlyTerminationRate로 이자 계산
5. 세금 차감 후 transService.credit()  (거래내역 FIXED_DEPOSIT_TERMINATE)
6. 상태 → TERMINATED
```

### 만기 (`POST /scheduler/maturity` 또는 매일 01시 자동 실행)

```
1. STATUS = 'ACTIVE' AND MATURITY_DATE <= 기준일 조회
2. 건별로 저장된 expectedInterest 지급   (거래내역 FIXED_DEPOSIT_MATURITY)
3. 상태 → MATURED
```

적금의 `savingsScheduler`와 동일하게 `FixedDepositScheduler`가 `@Scheduled(cron = "0 0 1 * * *")`로 매일 01시에 자동 실행되고, 같은 메서드를 컨트롤러가 수동 호출용으로도 노출한다. 앱에는 이미 `@EnableScheduling`이 걸려 있다.

## 작업 중 발견하고 대응한 사항

### 1. `@MapperScan`에 신규 패키지 등록 필요 (컨텍스트 로딩 실패)

통합 테스트 16건이 전부 `IllegalStateException`으로 실패했다. 원인은 MyBatis 매퍼 빈이 생성되지 않은 것이었다.

```
No qualifying bean of type
'com.hanati.bank.bankEx.deposit.fixed.mapper.FixedDepositProductMapper' available
```

`BankExApplication`이 `@MapperScan`으로 패키지를 **일일이 열거**하고 있어서, mybatis-spring-boot-starter의 자동 스캔이 동작하지 않았다.

```java
// 수정 전
@MapperScan({"com.hanati.bank.bankEx.loan", "com.hanati.bank.bankEx.deposit.savings"})

// 수정 후
@MapperScan({"com.hanati.bank.bankEx.loan", "com.hanati.bank.bankEx.deposit.savings",
		"com.hanati.bank.bankEx.deposit.fixed"})
```

향후 MyBatis 도메인을 추가할 때 같은 함정에 빠지므로 `CLAUDE.md` Conventions에 기록했다. 참고로 매퍼 XML은 `classpath:mapper/**/*.xml` 글롭이 잡아주므로 추가 설정이 필요 없다.

### 2. `terminate`가 기준일을 인자로 받도록 변경

중도해지 이자는 경과 개월 수에 비례하는데, 서비스 내부에서 `LocalDate.now()`를 호출하면 가입 당일에는 경과 0개월이 되어 **이자 계산 로직을 테스트로 검증할 수 없었다**.

같은 프로젝트에 이미 기준일을 주입하는 선례가 있어(`savingsMaturityService.execute(today)`, `autoTransferService.execute(date)`) 동일한 방식으로 맞췄다.

```java
public FixedDepositTerminateResponse terminate(String depositAccountId, LocalDate today)
```

컨트롤러가 `LocalDate.now()`를 넘긴다. 덕분에 "6개월 경과 후 해지 → 이자 25,000원" 케이스를 실제로 검증할 수 있게 됐다.

## 알려진 스코프 축소 및 미구현 항목

| 항목 | 상태 | 비고 |
|---|---|---|
| 프론트엔드 화면 | 미구현 | 명세 §2.1 구현 범위에 없다. 적금도 동일(`pages/deposit/savings/.gitkeep` 빈 폴더). |
| Swagger | 미적용 | 명세 §2.1은 "Swagger 또는 API 명세"를 요구하지만 프로젝트에 springdoc 의존성이 없다. 의존성 추가는 범위를 넘는다고 판단해 이 리포트의 API 표로 대체했다. |
| `CANCELLED` 상태 | 도달 불가 | 명세 4.4가 상태값으로 명시해 enum에는 넣었으나, 만기는 `MATURED`, 중도해지는 `TERMINATED`가 담당하므로 쓰이는 곳이 없다. 적금도 `MATURED`를 같은 식으로 미사용 상태로 둔다. 가입 당일 취소 같은 용도가 필요하면 추가 정의가 필요하다. |
| 중복 가입 제한 | 미적용 | 적금에는 `SAVINGS_DUPLICATED_SUBSCRIPTION`이 있으나, 정기예금은 목돈을 여러 건 예치하는 것이 자연스럽고 명세에도 없어 제외했다. |
| 만기 배치 실행 주기 | 매일 01시 | 적금과 동일한 cron(`0 0 1 * * *`). 적금 배치와 같은 시각이지만 Spring 기본 스케줄러가 단일 스레드라 순차 실행된다. 실서비스에서는 배치 실패 시 재시도·알림이 필요하다. |
| 복리 | 미지원 | 명세 4.5가 "초기 프로토타입에서는 단리 방식으로 구현한다"고 명시. |
| 만기 후 재예치 / 자동연장 | 미구현 | 명세 범위 밖. |
| 정기예금 계좌 자체의 거래내역 | 미구현 | 원금 출금·원리금 지급은 연결된 입출금계좌(`DEPOSIT_TRANSACTION`)에만 기록된다. 정기예금 계좌는 상태와 금액만 보관한다. |

### 향후 실서비스 전환 시 보완 필요 사항

- **세율 하드코딩**: `FixedDepositInterestCalculator.TAX_RATE = 0.154`가 상수다. 비과세·세금우대 상품을 다루려면 상품 또는 계좌 단위 과세구분이 필요하다.
- **금리 스냅샷만 저장**: 계좌에 `INTEREST_RATE`를 복사해 두어 상품 금리가 바뀌어도 기존 계좌는 영향받지 않는다. 다만 `terminate`는 **상품의 현재** `earlyTerminationRate`를 조회해 쓰므로, 중도해지 금리가 변경되면 기존 계좌에도 소급 적용된다. 실서비스에서는 이 값도 가입 시점에 계좌로 복사해야 한다.
- **동시성**: `terminate`와 만기 배치가 동시에 같은 계좌를 처리하면 이중 지급이 가능하다. 적금도 동일한 구조다. `deposit/transfer`처럼 비관적 락(`debitLocked`/`creditLocked`)을 적용하거나, 상태 기반 낙관적 업데이트(`UPDATE ... WHERE STATUS='ACTIVE'`)로 막아야 한다.
- **FK 제약 없음**: `FIXED_DEPOSIT_ACCOUNT`의 `USER_ID`, `DEPOSIT_PRODUCT_ID`, `WITHDRAW_ACCOUNT_NO`에 외래키가 없다. `schema.sql`의 다른 수신 테이블들도 동일하다.
- **본인 확인 없음**: `GET /{id}`, `POST /{id}/terminate`가 계좌 소유자를 검증하지 않아 계좌번호만 알면 조회·해지가 가능하다. bankEx 전체가 인증 체계 없이 동작하는 상태(`loginController`가 세션·JWT를 발급하지 않음)라 이 도메인만의 문제는 아니다.
