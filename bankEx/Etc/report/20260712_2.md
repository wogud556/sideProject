## 개요

수신(입출금계좌) 도메인에 동일 은행 내 계좌이체 기능을 추가했다. 명세는 `명세/이체.md`(예금주 조회, 이체 실행, 이체 결과 조회, 잔액/한도/비밀번호 검증, 트랜잭션 롤백, 중복 이체 방지까지 포함)로 사용자가 사전에 작성해 전달했다.

이번 작업은 사용자 요청에 따라 **planner → developer → reviewer → tester** 4단계 서브에이전트 파이프라인으로 진행했다. planner가 기존 코드(엔티티/리포지토리/서비스/컨트롤러/ErrorCode/application.yml/schema.sql/기존 테스트 스타일)를 직접 조사해 구현 계획을 작성했고, developer가 그 계획대로 구현, reviewer가 코드 리뷰로 버그 2건을 발견, developer가 재수정, tester가 테스트 74건을 작성·실행해 전부 통과시켰다.

명세와 실제 코드 사이에 두 가지 간극이 있어 구현 전 사용자에게 직접 확인했다:

1. **계좌 비밀번호**: 명세는 이체 시 "계좌 비밀번호" 검증을 요구하지만 기존 `ACCOUNT_INFO`에는 계좌별 비밀번호 컬럼이 없었다 (로그인 비밀번호만 존재). → **신규 도입**하기로 결정.
2. **1회/1일 이체한도**: 명세에 구체적 금액이 없었다. → **고정 기본값**(1회 5,000,000원 / 1일 10,000,000원)을 적용하기로 결정.

## 설계 결정 사항 (명세와 다르게 간 부분)

1. **신규 테이블 최소화**: 명세는 `ACCOUNT`, `ACCOUNT_TRANSACTION`, `ACCOUNT_TRANSFER` 3개 신규 테이블을 제안했지만, 기존에 이미 `AccountInfo`/`DepositTransaction`가 존재하고 기존 입출금·거래내역 조회 API가 이를 쓰고 있어 중복 생성하지 않고 **컬럼 확장**으로 처리했다. 이체 원장(`ACCOUNT_TRANSFER`)만 기존에 없는 개념이라 신규 엔티티로 만들었다.
2. **락 전략**: 출금/입금 두 계좌를 **계좌번호 문자열 사전순으로 정렬**해 `findByAccountNumberForUpdate`(PESSIMISTIC_WRITE, 기존에 이미 존재하던 쿼리)로 순서대로 잠근다. 상호 이체가 동시에 발생해도 항상 같은 순서로 잠그므로 데드락이 발생하지 않는다. 동일 계좌 요청 시 두 번째 락 조회는 생략한다.
3. **트랜잭션 원자성**: `transfer()` 전체를 하나의 `@Transactional`로 묶었다. 이로 인해 명세가 상정한 "이체 원장 PROCESSING → FAILED" 같은 영속적 중간 상태 전이는 이 구현에 존재하지 않는다 — 실패 시 원장 insert 자체가 롤백되어 아예 남지 않는다. 이는 "간단한 프로젝트" 스코프에 맞는 단순화이며, 오히려 전체 롤백 요구사항을 더 확실히 만족시킨다.
4. **중복 이체 방지 이중 방어**: `requestId` 사전 조회(빠른 경로) + `ACCOUNT_TRANSFER.REQUEST_ID` UNIQUE 제약 위반을 try/catch로 `DUPLICATE_TRANSFER_REQUEST`로 변환(동시 요청에 대한 최종 방어선). 사전 조회만으로는 두 요청이 동시에 들어올 때 레이스 컨디션을 막지 못하기 때문.
5. **거래번호 채번 재시도**: `TransactionNoGenerator`가 뽑은 번호가 극히 드물게 충돌하면(UNIQUE 위반) 최대 5회 재시도 후 실패 시 `TRANSFER_PROCESSING_FAILED`.
6. **거래내역 대표값**: 출금/입금 두 `DepositTransaction` 행에는 각자 다른 `transactionNumber`가 부여된다(유니크 제약 회피). 이체 실행/결과 조회 API 응답의 `transactionNumber`는 **출금 측 번호**를 대표값으로 사용한다.
7. **입금계좌 소유권은 검증하지 않음**: 타인 계좌로의 정상적인 이체를 막지 않아야 하므로 의도된 설계 (출금계좌만 로그인 고객 소유인지 검증).

## 코드 리뷰에서 발견되어 수정한 버그 (Critical/Major)

| 문제 | 조치 |
|---|---|
| `AccountInfo.perTransferLimit`/`dailyTransferLimit`가 nullable `Long`인데, 마이그레이션 미반영 등으로 값이 null인 계좌가 이체를 시도하면 언박싱 NPE → `BusinessException`이 아니라서 GlobalExceptionHandler가 못 잡고 500 그대로 노출 | `transferService.transfer()`에서 null이면 기본값(5,000,000/10,000,000)으로 취급하는 null-safe 처리 추가 |
| 거래번호 채번 충돌(UNIQUE 위반) 시 `DataIntegrityViolationException`이 잡히지 않고 500으로 노출 | `transService.recordTransferTransaction()`에 번호 재생성 후 최대 5회 재시도, 실패 시 `TRANSFER_PROCESSING_FAILED`로 변환하는 로직 추가 |

리뷰에서 함께 지적됐지만 **이번 스코프에서 고치지 않기로 판단**한 항목: (1) 이체 결과 조회/예금주 조회 API에 인증이 없어 임의 `transferId`/계좌번호로 조회 가능한 IDOR 성격의 문제, (2) 클라이언트가 보낸 `userId`를 그대로 신뢰(본인 인증 없음). 둘 다 이 프로젝트 전체에 세션/인증 계층 자체가 없는 기존 아키텍처의 연장선이며 이번 기능만의 회귀가 아니라서, 리스크로 기록만 하고 별도 인증 도입 작업으로 남겨뒀다. 계좌 비밀번호 평문 저장/비교도 기존 로그인 비밀번호와 동일한 방식이라 이번 스코프에서는 문제 삼지 않았다.

## 프론트엔드-백엔드 구현 격차 분석

백엔드 이체 기능 완성 후, 사용자 요청으로 프론트엔드(`bank_api.ts` + `pages/`) 전체를 백엔드 컨트롤러 목록과 대조해 "업무는 있는데 화면이 없는" 부분을 점검했다.

### 완전히 구현된 도메인
| 도메인 | 백엔드 API | 프론트 화면 |
|---|---|---|
| 로그인/회원가입/프로필 | login, signup, profile | `Login.tsx`, `Signup.tsx`, `MyPage.tsx` |
| 입출금계좌(일반) | 계좌 목록/단건/개설/해지, 입금/출금/거래내역 | `MyPage.tsx`(목록·개설), `AccountDetail.tsx`(입출금·거래내역·해지) |
| 일반대출 | 상품조회, 신청, 신청목록, 승인, 실행(지급), 상환 | `loan.tsx`(신청), `MyLoans.tsx`(승인·실행·상환) |
| 전세대출 | 상품조회, 신청, 심사, 실행 | `JeonseLoan.tsx` |

### 화면이 구현되지 않은 도메인

1. **계좌이체** (`deposit.transfer`, 이번에 만든 기능) — 백엔드 API 3개(예금주 조회, 이체 실행, 결과 조회)가 전부 존재하지만 `bank_api.ts`에 관련 함수가 하나도 없고, 이체 화면 자체가 없다. Home 메뉴에도 "이체" 항목이 없다.
2. **적금** (`deposit.savings`) — 상품조회/가입/단건조회/납입/해지, 스케줄러(자동이체·만기처리) 등 백엔드 API 7개가 전부 존재하지만 프론트에는 관련 함수·화면이 전혀 없다.

부수적으로, `loan.general`의 `GET /loan/validate-customer-account`(고객/계좌 검증용)는 어느 화면에서도 호출하지 않는다 — 내부 검증용으로 보여 우선순위는 낮다.

## 프론트엔드 폴더 구조 재편 (화면 미구현, 구조만 정리)

위 격차 분석 이후 사용자가 "화면 구현은 하지 않고, 구현해야 할 화면까지 포함해 업무단위로 폴더 구조만 정리해달라"고 요청했다. 백엔드가 `login`/`deposit.general`/`deposit.savings`/`deposit.transfer`/`loan.general`/`loan.jeonse`로 도메인 분리된 것과 대응시켜, 프론트 `pages/`도 동일한 업무단위 폴더로 재편했다. 화면 로직은 전혀 수정하지 않고 파일 위치와 import 경로만 변경했다.

`Home.tsx`(메인 메뉴)와 `MyPage.tsx`(프로필+계좌목록)는 특정 업무 하나에 속하지 않는 앱 전체의 셸/대시보드 성격이라, 도메인 폴더에 억지로 넣지 않고 별도 `common/` 폴더로 분리하기로 사용자와 확인했다.

### 최종 구조

```
pages/
├── common/           Home.tsx, MyPage.tsx        (특정 업무에 속하지 않는 공통 셸)
├── login/            Login.tsx, Signup.tsx
├── deposit/
│   ├── general/      AccountDetail.tsx
│   ├── savings/      (.gitkeep — 화면 미구현, 자리만 확보)
│   └── transfer/     (.gitkeep — 화면 미구현, 자리만 확보)
└── loan/
    ├── general/      loan.tsx, MyLoans.tsx
    └── jeonse/       JeonseLoan.tsx
```

- `git mv`로 이동해 파일 히스토리 보존
- 이동한 파일들의 상대경로 import(`../api`, `../components`, `../router`)를 폴더 깊이에 맞게 전부 수정 (`common`/`login`은 1단계 깊어져 `../../`, `deposit/general`/`loan/general`/`loan/jeonse`는 2단계 깊어져 `../../../`)
- `router/index_router.tsx`의 import 경로도 새 위치로 갱신
- `components/`(`Input`, `LoanApplicationForm` 등)는 여러 도메인이 공유하거나 도메인 결합이 약해 이번 재편 대상에서 제외
- `npm run build`(`tsc -b && vite build`) 성공 확인 — 화면 동작 변경 없음
