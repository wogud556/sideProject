클로드에게 전달할 수 있도록 **“전 업무를 완성하는 것이 아니라, 도메인별 최소 프로토타입을 구현하는 기준”**으로 정리했습니다.

bankEx 신규 업무 도메인 프로토타입 개발 명세

1. 개발 목표

현재 bankEx 프로젝트에 존재하지 않거나 분리되어 있는 업무를 대상으로, 전체 은행 업무를 완성하는 수준이 아닌 기본 흐름을 확인할 수 있는 최소 프로토타입을 구현한다.

이번 개발 범위는 다음과 같다.

1. 일반대출 이자 계산 보완
2. 정기예금 업무 신규 추가
3. 카드 업무 최소 프로토타입
4. 외환 업무 최소 프로토타입
5. 알림 및 OTP 인증 구조 추가
6. Screening 프로젝트 정리 및 대출 심사 연계 방향 결정

모든 업무를 한 번에 완성하지 않고, 각 도메인의 핵심 엔티티와 기본 API가 동작하는 수준까지 구현한다.

3. 일반대출 이자 계산 보완

3.1 목적

현재 일반대출 상환 시 원금만 차감되며 상품의 interestRate가 실제 계산에 사용되지 않는다.

이를 개선하여 최소한 다음 정보를 계산할 수 있도록 한다.

- 월 납부 이자
- 원금 상환액
- 총 상환액
- 상환 후 잔여 원금

⸻

3.2 초기 지원 상환 방식

프로토타입에서는 다음 두 방식만 우선 지원한다.

EQUAL_PRINCIPAL
- 원금균등상환
BULLET
- 만기일시상환

원리금균등상환은 계산 구조를 확장할 수 있도록 인터페이스만 고려하고, 초기 구현에서는 제외 가능하다.

⸻

3.3 핵심 계산

월 이자율 = 연 이자율 / 12
월 이자 = 상환 전 잔여 원금 × 월 이자율

금액 계산은 반드시 BigDecimal을 사용한다.

⸻

3.4 상환 처리

기존 repay()를 다음 순서로 변경한다.

1. 대출 계약 조회
2. 상품 금리 또는 계약 적용금리 조회
3. 현재 회차 이자 계산
4. 납부금액을 이자와 원금으로 분리
5. 잔여 원금 차감
6. 상환 내역 저장
7. 거래내역 생성
8. 잔여 원금이 0원이면 대출 완료 처리

상환 응답 예시:

{
  "loanId": 1001,
  "paymentAmount": 520000,
  "principalAmount": 480000,
  "interestAmount": 40000,
  "remainingPrincipal": 9520000,
  "status": "ACTIVE"
}

9. Screening 프로젝트 정리

9.1 현재 문제

Screening 프로젝트가 bankEx와 분리되어 있으며, bankEx의 대출 및 전세대출 도메인에서 참조하지 않는다.

현재 대출 심사 로직이 다음과 같이 분산되어 있을 가능성이 있다.

Screening 별도 프로젝트
일반대출 내부 심사 로직
전세대출 jeonseReviewService

이 상태에서는 심사 기준이 중복되고 업무별 결과가 달라질 수 있다.

⸻

9.2 우선 분석 작업

클로드는 구현 전에 다음 내용을 조사한다.

1. Screening 프로젝트의 엔티티, 서비스, API 목록
2. 일반대출 내부 심사 로직
3. jeonseReviewService 심사 항목
4. 중복되는 심사 조건
5. Screening 프로젝트가 현재 정상 실행 가능한지
6. bankEx와 연계 가능한 구조인지

분석 결과를 다음 형태로 작성한다.

- 유지 가능
- bankEx 내부로 통합 권장
- 별도 심사 서비스로 연계 권장
- 폐기 권장

⸻

9.3 권장 방향

프로토타입에서는 bankEx 내부에 공통 심사 인터페이스를 만든다.

public interface LoanScreeningService {
    ScreeningResult screen(ScreeningRequest request);
}

⸻

9.4 초기 심사 규칙

프로토타입에서는 단순 규칙 기반으로 구현한다.

예시:

신용점수 600점 미만
→ REJECTED
연소득 대비 신청금액이 500% 초과
→ MANUAL_REVIEW
기존 대출금과 신규 신청금액 합계가 내부 기준 초과
→ REJECTED
기본 조건 충족
→ APPROVED

실제 금융기관의 신용평가 및 DSR 기준을 구현하는 것이 아니라 테스트용 내부 기준으로 작성한다.

⸻

9.5 Screening 프로젝트 처리 기준

방안 A: bankEx 내부 통합

Screening 프로젝트 기능이 작고 단순 규칙 기반이면 bankEx의 screening 도메인으로 이동한다.

방안 B: 별도 서비스 유지

독립 실행 가능하고 향후 여러 금융 업무에서 사용할 예정이면 REST API 기반 별도 서비스로 유지한다.

POST /api/screenings/loans
GET  /api/screenings/{screeningId}

방안 C: 폐기

현재 코드가 사용되지 않고 jeonseReviewService보다 기능이 부족하면 필요한 로직만 이관한 후 제거한다.

클로드는 임의로 삭제하지 말고 분석 보고서와 권장안을 먼저 제공한다.

10. 개발 우선순위

1순위: 일반대출 이자 계산

현재 사용자에게 노출된 금리가 상환에 반영되지 않는 기능 오류에 가까운 문제이므로 가장 먼저 처리한다.

- 이자 계산기
- 상환 응답 개선
- 상환 내역
- 테스트

13. 클로드 최종 작업 지시

현재 프로젝트 전체를 먼저 분석하고 기존 구현 방식과 최대한 동일한 형태로 작업한다.

신규 도메인을 모두 완성하려 하지 말고 각 업무의 핵심 흐름이 실행되는 최소 프로토타입을 구현한다.

각 업무는 독립된 패키지로 구성하되, 계좌, 고객, 거래내역, 인증과 같은 공통 기능은 기존 코드를 재사용한다.

대출 이자, 예금 이자, 환율, 카드 한도 등의 숫자 계산은 BigDecimal을 사용한다.

계좌 잔액 변경, 대출 상환, 카드 결제, 환전 처리는 반드시 트랜잭션으로 처리한다.

실제 외부 연동은 구현하지 않고 다음과 같이 인터페이스와 Mock 구현을 사용한다.

SMS 발송 → MockSmsSender
푸시 발송 → MockPushSender
환율 조회 → MockExchangeRateProvider
신용평가 → RuleBasedScreeningService
카드 승인 → InternalCardAuthorizationService

개발 완료 후 다음 결과물을 제공한다.

4. DB DDL
5. 신규 API 목록
6. 주요 업무 흐름
7. 테스트 결과

9. 미구현 항목
10. 향후 실서비스 전환 시 필요한 보완 사항

특히 Screening 프로젝트는 분석 전 삭제하거나 통합하지 말고, 현재 활용 가능성과 중복 여부를 먼저 보고한다.
