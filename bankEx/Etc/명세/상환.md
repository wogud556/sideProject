아래 내용을 그대로 Claude에게 전달할 수 있도록 **개발 명세 형태**로 정리했어. 현재 프로젝트의 Spring Boot 구조를 먼저 분석하고 기존 기능을 최대한 유지하도록 조건도 포함했어.

# 대출 원리금 상환 코어 개발 명세

## 1. 개발 목적

은행 앱의 화면 기능이 아니라 대출 코어 시스템에서 사용하는 원리금 상환 업무를 구현한다.

이번 개발의 핵심 목표는 다음과 같다.

- 대출계좌에 입금된 상환금을 정해진 우선순위에 따라 배분한다.
- 정기 상환, 부분 상환, 중도상환, 전액 상환을 지원한다.
- 모든 상환 거래를 원장 형태로 기록한다.
- 상환 취소 시 데이터를 삭제하거나 직접 복구하지 않고 역거래를 생성한다.
- 동일 요청이 중복 처리되지 않도록 멱등성을 보장한다.
- 상품별로 상환금 배분 정책을 변경할 수 있도록 설계한다.

---

## 2. 개발 전 확인 사항

구현 전에 현재 프로젝트를 분석하고 다음 내용을 먼저 보고한다.

1. 현재 대출 관련 패키지와 클래스 구조
2. 대출계좌, 상환 스케줄, 거래내역 관련 엔티티
3. 기존 상환 서비스와 API
4. 금리 및 이자 계산 방식
5. 데이터베이스 접근 방식
6. 공통 응답 및 예외 처리 방식
7. 기존 테스트 구조
8. 이번 기능과 충돌하거나 중복되는 코드

분석 결과와 구현 계획을 먼저 제시한 다음 개발을 시작한다.

기존 API와 데이터 구조는 가능한 한 유지하되, 원리금 상환의 정확성과 거래 추적을 위해 필요한 변경은 이유와 영향 범위를 설명한다.

---

## 3. 개발 범위

다음 상환 유형을 지원한다.

### 3.1 정기 상환

상환 스케줄의 납부예정일과 회차를 기준으로 원금과 이자를 상환한다.

### 3.2 자동이체 상환

등록된 출금계좌에서 납부예정금액을 출금하고 대출계좌에 상환 처리한다.

실제 외부 계좌 시스템과 연동하지 않는 경우 출금 성공·실패를 처리할 수 있는 인터페이스와 Mock 구현체를 제공한다.

### 3.3 수동 납부

창구, 관리자 또는 별도 채널에서 입력한 금액을 대출계좌에 상환한다.

### 3.4 부분 상환

납부예정금액보다 적은 금액이 입금된 경우에도 상환 가능한 항목까지만 배분한다.

미납 금액은 잔존 채무로 유지한다.

### 3.5 중도상환

약정된 상환 스케줄과 별개로 원금의 일부를 조기 상환한다.

중도상환 이후 처리 방식은 정책으로 분리한다.

- 만기 유지 후 이후 회차 납부금액 재산정
- 납부금액 유지 후 만기 단축
- 스케줄을 변경하지 않고 원금만 감소

이번 구현에서 지원하지 않는 방식은 명확히 표시한다.

### 3.6 전액 상환

기준일 현재 고객이 납부해야 할 전체 금액을 계산하고 상환한다.

전액 상환 예정금액에는 다음 항목이 포함될 수 있다.

- 정상 원금
- 연체 원금
- 정상 이자
- 미수 이자
- 연체 이자
- 중도상환수수료
- 기타 비용

모든 잔존 채무가 0원이 된 경우에만 대출계좌를 완제 상태로 변경한다.

### 3.7 상환 취소

완료된 상환 거래를 삭제하지 않고 원거래와 반대되는 역거래를 생성한다.

취소 시 다음 내용을 복원한다.

- 원금잔액
- 정상 이자
- 연체 원금
- 연체 이자
- 비용과 수수료
- 상환 스케줄 납부 상태
- 대출계좌 상태

이미 취소된 거래는 다시 취소할 수 없다.

취소 이후 다른 거래가 존재하여 원상 복구가 불가능하거나 잔액 정합성이 깨지는 경우에는 취소를 거절하고 명확한 오류를 반환한다.

### 3.8 과오납 환급

납부금액이 전액 상환 예정금액보다 큰 경우 초과 금액을 과오납으로 관리한다.

과오납은 대출 원금을 음수로 만들지 않는다.

환급 처리 시 별도 환급 거래를 기록하고 다음 상태를 관리한다.

- 환급 대기
- 환급 완료
- 환급 실패
- 환급 취소

## 4. 상환금 배분 정책

기본 상환금 배분 순서는 다음과 같다.

```text
비용
→ 연체이자
→ 정상 이자
→ 연체원금
→ 정상원금
→ 과오납
```

하나의 항목을 전부 상환한 후 남은 금액을 다음 항목에 배분한다.

예시:

```text
납부금액: 100,000원

비용:       10,000원
연체이자:   20,000원
정상이자:   30,000원
연체원금:   50,000원
```

배분 결과:

```text
비용 상환:       10,000원
연체이자 상환:   20,000원
정상이자 상환:   30,000원
연체원금 상환:   40,000원
남은 연체원금:   10,000원
```

배분 순서를 서비스 코드에 직접 작성하지 않는다.

다음과 같은 정책 인터페이스를 사용한다.

```java
public interface RepaymentAllocationPolicy {

    RepaymentAllocationResult allocate(
        RepaymentAllocationContext context
    );
}
```

기본 구현체 예시:

```java
DefaultRepaymentAllocationPolicy
```

향후 상품별 정책을 추가할 수 있어야 한다.

```java
GeneralLoanRepaymentAllocationPolicy
JeonseLoanRepaymentAllocationPolicy
DelinquentLoanRepaymentAllocationPolicy
```

정책은 대출상품 또는 상품 유형에 따라 선택한다.

## 5. 회차별 배분 규칙

미납 회차가 여러 개라면 납부예정일이 오래된 회차부터 처리한다.

기본 처리 순서:

```text
가장 오래된 미납 회차
→ 다음 미납 회차
→ 현재 회차
→ 미래 원금
```

각 회차 안에서는 상환금 배분 정책을 적용한다.

동일 날짜의 스케줄이 여러 건인 경우 순서를 결정할 수 있는 명확한 정렬 기준을 둔다.

예:

```text
납부예정일 오름차순
→ 회차 오름차순
→ 스케줄 ID 오름차순
```

## 6. 주요 도메인 모델

현재 프로젝트의 기존 엔티티를 우선 활용한다. 필요한 모델이 없다면 아래 구조를 참고하여 추가한다.

### 6.1 LoanAccount

대출계좌의 현재 상태와 잔액을 관리한다.

주요 속성:

```text
id
loanAccountNumber
customerId
productId
status
originalPrincipal
principalBalance
overduePrincipal
accruedInterest
overdueInterest
feeBalance
disbursementDate
maturityDate
lastTransactionDate
version
```

대출계좌 상태 예시:

```text
PENDING
ACTIVE
PAST_DUE
DELINQUENT
PAID_OFF
CLOSED
```

### 6.2 RepaymentSchedule

회차별 납부예정금액과 납부 결과를 관리한다.

주요 속성:

```text
id
loanAccountId
installmentNumber
dueDate
scheduledPrincipal
scheduledInterest
paidPrincipal
paidInterest
overduePrincipal
overdueInterest
status
paidAt
```

상태 예시:

```text
SCHEDULED
PARTIALLY_PAID
PAID
OVERDUE
CANCELLED
```

### 6.3 RepaymentTransaction

상환 요청 한 건을 나타내는 거래 헤더다.

주요 속성:

```text
id
transactionNumber
loanAccountId
transactionType
paymentMethod
requestedAmount
allocatedAmount
overpaymentAmount
status
businessDate
processedAt
idempotencyKey
originalTransactionId
createdBy
```

거래 유형 예시:

```text
REGULAR_REPAYMENT
MANUAL_REPAYMENT
PARTIAL_REPAYMENT
PREPAYMENT
FULL_REPAYMENT
REPAYMENT_REVERSAL
OVERPAYMENT_REFUND
```

거래 상태 예시:

```text
REQUESTED
COMPLETED
FAILED
REVERSED
```

### 6.4 RepaymentAllocation

상환금이 어떤 채무 항목에 얼마씩 배분되었는지 기록한다.

주요 속성:

```text
id
repaymentTransactionId
repaymentScheduleId
allocationType
allocatedAmount
allocationOrder
```

배분 유형:

```text
FEE
OVERDUE_INTEREST
INTEREST
OVERDUE_PRINCIPAL
PRINCIPAL
OVERPAYMENT
```

한 번 완료된 배분 결과는 수정하지 않는다. 취소가 필요하면 역거래와 반대 방향의 배분 내역을 추가한다.

## 7. 처리 흐름

### 7.1 일반 상환 처리

```text
1. 요청값 검증
2. 멱등성 키 확인
3. 대출계좌 조회 및 잠금
4. 대출계좌 상태 검증
5. 기준일 현재 채무 금액 계산
6. 적용할 상환금 배분 정책 선택
7. 미납 회차부터 상환금 배분
8. 대출계좌 잔액 갱신
9. 상환 스케줄 납부 상태 갱신
10. 상환 거래 및 배분 내역 저장
11. 회계 이벤트 생성
12. 완제 여부 판단
13. 처리 결과 반환
```

전체 과정은 하나의 데이터베이스 트랜잭션으로 처리한다.

### 7.2 전액 상환 처리

```text
1. 전액 상환 예상금액 조회
2. 예상금액의 유효시간 또는 기준일 확인
3. 실제 처리 시점의 금액 재계산
4. 요청금액과 재계산 금액 비교
5. 전체 채무 항목에 배분
6. 잔존 채무 확인
7. 잔존 채무가 0이면 PAID_OFF 처리
8. 초과 금액은 과오납 처리
```

조회한 예상금액과 실제 상환 처리 사이에 날짜가 바뀌거나 이자가 추가될 수 있으므로 처리 시점에 금액을 다시 검증한다.

### 7.3 상환 취소 처리

```text
1. 원거래 조회
2. 원거래 완료 상태 확인
3. 기존 취소 여부 확인
4. 후속 거래 존재 여부 확인
5. 취소 가능 여부 검증
6. 원거래 배분 내역을 기반으로 역배분 생성
7. 대출계좌 잔액 복구
8. 상환 스케줄 상태 복구
9. 원거래를 REVERSED 상태로 변경
10. 취소 거래 저장
11. 반대 회계 이벤트 생성
```

## 8. API 명세

현재 프로젝트의 API 명명 규칙과 공통 응답 형식을 우선 적용한다.

### 8.1 상환 예정금액 조회

```http
GET /api/loans/{loanAccountId}/repayment-quote
```

조회 조건 예시:

```text
repaymentType
paymentDate
requestedPrincipalAmount
```

응답 예시:

```json
{
  "loanAccountId": 1,
  "quoteDate": "2026-10-04",
  "repaymentType": "FULL_REPAYMENT",
  "principal": 10000000,
  "overduePrincipal": 0,
  "interest": 45000,
  "overdueInterest": 0,
  "fee": 50000,
  "totalAmount": 10095000,
  "validUntil": "2026-10-04T23:59:59"
}
```

### 8.2 상환 실행

```http
POST /api/loans/{loanAccountId}/repayments
```

요청 예시:

```json
{
  "repaymentType": "REGULAR_REPAYMENT",
  "paymentMethod": "MANUAL",
  "amount": 500000,
  "paymentDate": "2026-10-04",
  "idempotencyKey": "repayment-20261004-000001"
}
```

응답 예시:

```json
{
  "transactionNumber": "RP20261004000001",
  "loanAccountId": 1,
  "requestedAmount": 500000,
  "allocatedAmount": 500000,
  "overpaymentAmount": 0,
  "status": "COMPLETED",
  "allocations": [
    {
      "type": "INTEREST",
      "amount": 50000
    },
    {
      "type": "PRINCIPAL",
      "amount": 450000
    }
  ],
  "remainingPrincipal": 9550000
}
```

### 8.3 전액 상환

```http
POST /api/loans/{loanAccountId}/repayments/full
```

### 8.4 상환 취소

```http
POST /api/loans/{loanAccountId}/repayments/{transactionNumber}/reversal
```

요청 예시:

```json
{
  "reason": "고객 이중 납부 확인",
  "idempotencyKey": "reversal-20261004-000001"
}
```

### 8.5 상환 거래내역 조회

```http
GET /api/loans/{loanAccountId}/repayments
GET /api/loans/{loanAccountId}/repayments/{transactionNumber}
```

### 8.6 과오납 환급

```http
POST /api/loans/{loanAccountId}/overpayments/{overpaymentId}/refund
```

## 9. 필수 검증 규칙

다음 조건을 반드시 검증한다.

- 납부금액은 0보다 커야 한다.
- 존재하지 않는 대출계좌는 처리할 수 없다.
- 실행 전 또는 종료된 대출은 상환할 수 없다.
- 이미 완제된 대출은 추가 상환할 수 없다.
- 동일한 멱등성 키는 한 번만 처리한다.
- 대출 원금잔액은 음수가 될 수 없다.
- 이자·비용 잔액도 음수가 될 수 없다.
- 상환 스케줄의 납부금액은 예정금액을 비정상적으로 초과할 수 없다.
- 초과 납부금액은 과오납으로 분리한다.
- 상환일이 대출 실행일보다 빠를 수 없다.
- 이미 취소된 상환은 다시 취소할 수 없다.
- 다른 대출계좌의 상환 거래를 취소할 수 없다.
- 원거래 금액과 배분 합계가 일치해야 한다.
- 배분금액과 과오납 합계는 요청금액과 일치해야 한다.

금액 계산에는 `double` 또는 `float`을 사용하지 않는다. Java의 `BigDecimal`을 사용하고 반올림 규칙을 명시한다.

## 10. 동시성 및 멱등성

동일 대출계좌에 동시에 여러 상환 요청이 들어올 수 있다.

다음 중 현재 프로젝트에 적합한 방법을 선택하여 적용한다.

- 비관적 잠금
- 낙관적 잠금과 재시도
- 대출계좌 단위 직렬 처리

최소 요구사항:

- 동일 상환 요청의 중복 실행 방지
- 동시에 처리된 상환으로 인한 원금 음수 방지
- 스케줄 중복 납부 방지
- 전액 상환과 일반 상환의 동시 실행 방지
- 멱등성 키에 고유 제약조건 적용
- 동시성 충돌 테스트 작성

## 11. 회계 이벤트

상환 거래가 완료되면 회계 시스템이 사용할 수 있는 이벤트를 생성한다.

예시:

```text
LOAN_PRINCIPAL_REPAID
LOAN_INTEREST_RECEIVED
OVERDUE_INTEREST_RECEIVED
REPAYMENT_REVERSED
OVERPAYMENT_RECEIVED
OVERPAYMENT_REFUNDED
LOAN_PAID_OFF
```

이번 범위에서 실제 복식부기 분개까지 구현하지 않는다면 이벤트와 Outbox 테이블까지만 구현한다.

상환 거래 저장과 Outbox 이벤트 저장은 동일한 데이터베이스 트랜잭션으로 처리한다.

## 13. 테스트 요구사항

단위 테스트와 통합 테스트를 모두 작성한다.

### 13.1 배분 정책 단위 테스트

- 비용만 전액 상환
- 비용과 연체이자 상환
- 정상 이자까지 상환
- 일부 원금 상환
- 모든 채무 상환
- 채무보다 큰 금액 납부
- 납부금액 0원
- 음수 납부금액
- 배분 합계 검증
- 여러 미납 회차가 있을 때 오래된 회차 우선 처리

### 13.2 상환 서비스 테스트

- 정상 정기 상환
- 부분 상환
- 중도상환
- 전액 상환 및 완제 처리
- 과오납 생성
- 동일 멱등성 키 재요청
- 상환 취소
- 상환 취소 후 잔액 복구
- 취소 거래 재취소 차단
- 후속 거래가 있는 원거래 취소 차단
- 완제된 계좌에 대한 상환 차단

### 13.3 동시성 테스트

- 동일 계좌에 두 개의 상환 요청 동시 실행
- 남은 원금보다 큰 두 요청 동시 실행
- 동일 멱등성 키 동시 요청
- 전액 상환과 일반 상환 동시 요청
- 상환과 상환 취소 동시 요청

### 13.4 정합성 검증

각 테스트에서 다음 불변조건을 검증한다.

```text
요청금액
= 배분금액 합계 + 과오납금액

현재 원금잔액
= 이전 원금잔액 - 원금 배분액 + 원금 취소액

스케줄 납부금액
= 해당 스케줄 배분내역 합계

원거래 배분 합계
= 취소 거래 역배분 합계
```

## 14. 완료 조건

다음 조건을 모두 만족해야 개발 완료로 판단한다.

- 상환금이 정책에 따라 정확하게 배분된다.
- 미납 회차가 오래된 순서로 처리된다.
- 모든 상환과 취소가 원장에 기록된다.
- 상환 취소가 역거래 방식으로 동작한다.
- 대출계좌 잔액과 상환 스케줄의 정합성이 유지된다.
- 중복 요청이 두 번 처리되지 않는다.
- 동시 요청에서도 원금이 음수가 되지 않는다.
- 전액 상환 후 잔존 채무가 없을 때만 완제 처리된다.
- 초과 납부금액이 과오납으로 분리된다.
- 주요 업무 규칙에 대한 단위 테스트가 존재한다.
- API 통합 테스트가 통과한다.
- 기존 테스트가 깨지지 않는다.
- 주요 설계 결정과 실행 방법이 문서화된다.
