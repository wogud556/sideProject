좋아! 👍

그럼 기존에 개발하고 있는 **`bankEx` 프로젝트에 주택담보대출(주담대) 기능을 추가하는 방향**으로 정리해 볼게.

현재 프로젝트에서 사용하고 있는 기술 스택을 기준으로 설계하겠어.

- **Frontend:** React + TypeScript + Vite
- **상태 관리:** Zustand
- **API 통신:** Axios
- **데이터 검증:** Zod
- **Backend:** Spring Boot
- **Persistence:** MyBatis
- **DB:** 관계형 데이터베이스 기준

이번에는 단순히 주담대 계산기를 만드는 것이 아니라, **실제 은행의 주택담보대출 업무 흐름을 학습하고 구현할 수 있는 여신 시스템**을 목표로 잡는 게 좋아.

# 1. 주택담보대출 시스템의 전체 구조

주담대 업무는 크게 7개 영역으로 나눌 수 있어.

| 영역      | 주요 기능                           | 중요도 |
| --------- | ----------------------------------- | ------ |
| 대출 신청 | 고객정보, 주택정보, 신청금액 등록   | 필수   |
| 담보 관리 | 주택 시세, 감정가, 선순위 채권 관리 | 필수   |
| 한도 산정 | LTV, DTI, DSR 계산                  | 필수   |
| 여신 심사 | 신용평가, 소득심사, 규제 검증       | 필수   |
| 대출 승인 | 승인금액, 금리, 대출기간 확정       | 필수   |
| 대출 실행 | 대출계좌 생성, 실행금 지급          | 필수   |
| 사후 관리 | 이자, 원금상환, 연체, 중도상환      | 필수   |

업무 프로세스는 다음과 같이 설계할 수 있어.

```text
[고객]
   │
   ▼
주택담보대출 신청
   │
   ▼
고객 및 소득정보 조회
   │
   ▼
담보물건 등록
   │
   ▼
담보가치 평가
   │
   ▼
대출한도 산정
   ├── LTV
   ├── DTI
   ├── DSR
   └── 상품별 규제
   │
   ▼
여신 심사
   ├── 신용심사
   ├── 상환능력 심사
   ├── 담보 적격성 심사
   └── 규제 적합성 검증
   │
   ▼
대출 승인
   │
   ▼
대출 약정
   │
   ▼
담보권 설정 확인
   │
   ▼
대출 실행
   │
   ▼
원리금 상환 및 사후 관리
```

핵심은 **대출 신청, 심사, 승인, 실행, 상환을 독립적인 업무 단계로 구분하는 것**이야.

예를 들어 심사가 승인되었다고 해서 대출금이 즉시 지급되는 것은 아니야. 약정과 담보권 설정 등 실행 선행조건을 충족해야 실제 대출 실행이 가능하도록 설계해야 해.

bankEx

│       │       ├── MortgageCollateral.tsx
│       │       ├── MortgageLimit.tsx
│       │       ├── MortgageScreening.tsx
│       │       ├── MortgageApproval.tsx
│       │       ├── MortgageExecution.tsx
│       │       └── MortgageRepayment.tsx
│       │
│       ├── api
│       │   └── mortgageApi.ts
│       │
│       ├── stores
│       │   └── mortgageStore.ts
│       │
│       └── schemas
│           └── mortgageSchema.ts

        ├── limit

각 백엔드 모듈은 필요에 따라 다음 계층으로 구성하면 돼.

```text

├── controller
├── service
├── domain
├── dto
└── mapper
```

기존 고객 관리, 수신 계좌, 여신 계좌, 공통 심사 기능이 있다면 새로 만들지 말고 재사용하는 구조가 적절해.

# 3. 데이터베이스 설계

주담대는 신청 데이터와 실제 대출계좌 데이터를 반드시 구분해야 해.

신청이 거절되거나 고객이 철회할 수도 있기 때문이야.

### 핵심 테이블

| 테이블                        | 설명                       |
| ----------------------------- | -------------------------- |
| `MORTGAGE_APPLICATION`        | 주담대 신청 원장           |
| `MORTGAGE_PROPERTY`           | 담보 부동산 정보           |
| `MORTGAGE_VALUATION`          | 담보 평가 이력             |
| `MORTGAGE_LIEN`               | 선순위 채권 및 담보권 정보 |
| `MORTGAGE_INCOME`             | 소득 심사 정보             |
| `MORTGAGE_DEBT`               | 기존 부채 정보             |
| `MORTGAGE_LIMIT_RESULT`       | LTV·DTI·DSR 산정 결과      |
| `MORTGAGE_SCREENING`          | 여신 심사 결과             |
| `MORTGAGE_APPROVAL`           | 대출 승인 정보             |
| `MORTGAGE_AGREEMENT`          | 대출 약정                  |
| `MORTGAGE_EXECUTION`          | 대출 실행 이력             |
| `MORTGAGE_REPAYMENT_SCHEDULE` | 원리금 상환 예정표         |
| `MORTGAGE_REPAYMENT_HISTORY`  | 실제 상환 거래 이력        |

실제 대출계좌는 기존 `bankEx`의 공통 여신계좌 테이블과 연결하는 것을 추천해.

### 주요 관계

```text
CUSTOMER
   │
   └── MORTGAGE_APPLICATION
          │
          ├── MORTGAGE_PROPERTY
          │       ├── MORTGAGE_VALUATION
          │       └── MORTGAGE_LIEN
          │
          ├── MORTGAGE_INCOME
          ├── MORTGAGE_DEBT
          ├── MORTGAGE_LIMIT_RESULT
          ├── MORTGAGE_SCREENING
          ├── MORTGAGE_APPROVAL
          └── MORTGAGE_AGREEMENT
                  │
                  └── LOAN_ACCOUNT
                         ├── MORTGAGE_EXECUTION
                         ├── MORTGAGE_REPAYMENT_SCHEDULE
                         └── MORTGAGE_REPAYMENT_HISTORY
```

이 구조에서는 신청부터 실행까지의 이력을 추적할 수 있고, 실제 대출 실행 이후에는 공통 여신계좌를 중심으로 잔액과 거래를 관리할 수 있어.

# 4. 주담대 한도 산정 엔진 설계

이번 개발에서 가장 중요한 부분이야.

주담대 한도 산정 엔진은 단순히 LTV, DSR을 계산하는 기능이 아니라 **여러 심사 기준을 적용해 최종 대출 가능 금액을 결정하는 엔진**으로 설계하는 게 좋아.

## 4.1 한도 산정 구조

```text
MortgageLimitService
        │
        ▼
MortgageLimitEngine
        │
        ├── LtvCalculator
        │      └── 담보가치 기반 한도
        │
        ├── DtiCalculator
        │      └── 소득 대비 상환부담
        │
        ├── DsrCalculator
        │      └── 전체 부채 원리금
        │
        ├── StressDsrCalculator
        │      └── 스트레스 금리 적용
        │
        ├── CollateralLimitCalculator
        │      └── 선순위 채권 등 반영
        │
        └── RegulatoryLimitPolicy
               └── 지역·상품·차주별 규제
        │
        ▼
최종 대출한도 산정
```

### 계산 예시

다음 조건을 가정해 보자.

| 항목       |         값 |
| ---------- | ---------: |
| 주택가격   |     5억 원 |
| 담보평가액 |     5억 원 |
| LTV        |        70% |
| 연소득     | 6,500만 원 |
| DSR 한도   |        40% |
| 신청금액   |     3억 원 |
| 대출금리   |         4% |
| 대출기간   |       30년 |

먼저 LTV 한도를 계산해.

```java
BigDecimal ltvLimit = collateralValue
    .multiply(ltvRate)
    .divide(
        BigDecimal.valueOf(100),
        0,
        RoundingMode.DOWN
    );
```

LTV 한도는 3억 5,000만 원이야.

그다음 DSR 기준 한도를 산출하고, 상품 및 규제별 한도를 함께 적용해.

```java
BigDecimal finalLimit = Stream.of(
        ltvLimit,
        dsrLimit,
        productLimit,
        regulatoryLimit
    )
    .min(BigDecimal::compareTo)
    .orElse(BigDecimal.ZERO);
```

여기서 `dsrLimit`은 DSR 비율 자체가 아니라, 기존 부채의 상환액과 대출 조건을 반영해 **대출원금으로 역산한 금액**이어야 해.

또한 실제 담보가용액 계산은 선순위 채권과 임대차 관계 등을 고려해야 하므로 단순 LTV 계산과 분리하는 것이 좋아.

# 5. 규제 정책 엔진 설계

은행 시스템에서는 규제 비율을 소스 코드에 직접 입력하면 안 돼.

예를 들어 다음과 같이 작성하는 것은 피하는 게 좋아.

```java
double ltv = 70;
double dsr = 40;
```

주택담보대출 규제는 시행일, 지역, 차주 조건, 상품에 따라 변경될 수 있기 때문이야.

따라서 별도의 정책 테이블을 추천해.

### MORTGAGE_POLICY

| 컬럼           | 설명                |
| -------------- | ------------------- |
| POLICY_ID      | 정책 식별자         |
| POLICY_TYPE    | LTV, DTI, DSR 등    |
| REGION_CODE    | 적용 지역           |
| BORROWER_TYPE  | 차주 유형           |
| PRODUCT_CODE   | 대출상품            |
| POLICY_VALUE   | 규제 비율 또는 한도 |
| EFFECTIVE_FROM | 적용 시작일         |
| EFFECTIVE_TO   | 적용 종료일         |
| POLICY_VERSION | 정책 버전           |
| CREATED_AT     | 등록일              |

정책 엔진은 다음 순서로 동작하도록 설계하면 돼.

1. 대출 신청일 및 심사 기준일 확인
2. 주택 소재지 및 규제지역 여부 확인
3. 차주의 주택 보유 수와 대출 목적 확인
4. 해당 상품에 적용할 정책 조회
5. LTV·DTI·DSR 등 한도 계산
6. 적용된 정책 버전과 산정 결과 저장

이렇게 하면 향후 정책이 변경되더라도 기존 심사 결과를 재현할 수 있어.

실제 운영 수준을 목표로 한다면 정책 테이블에는 적용 우선순위, 예외 조건, 승인 상태, 정책 근거도 추가하는 게 좋아.

# 6. 여신 심사 프로세스 설계

주담대 심사는 크게 세 가지로 분리할 수 있어.

| 심사 영역 | 검증 내용                     |
| --------- | ----------------------------- |
| 차주 심사 | 신용, 소득, 재직, 기존 부채   |
| 담보 심사 | 담보가치, 소유권, 선순위 권리 |
| 규제 심사 | LTV, DTI, DSR, 상품 적격성    |

심사 결과도 단순 승인·거절만으로 처리하지 않는 것을 추천해.

```java
public enum ScreeningStatus {
    PENDING,
    IN_PROGRESS,
    ADDITIONAL_DOCUMENT_REQUIRED,
    APPROVED,
    CONDITIONALLY_APPROVED,
    REJECTED
}
```

특히 `CONDITIONALLY_APPROVED`는 실제 업무 흐름을 구현하는 데 유용해.

예를 들어 고객의 상환능력 심사는 통과했지만 담보 관련 서류가 부족한 경우, 추가 서류 제출을 조건으로 승인할 수 있어.

다만 조건부 승인은 최종 대출 실행 가능 상태와 구분해야 해.

# 7. 대출 실행 및 상환 시스템

심사 이후에는 기존 `bankEx`의 여신계좌 기능과 연계하는 것이 핵심이야.

### 실행 처리

```text
대출 승인
    ↓
대출 약정
    ↓
실행 선행조건 검증
    ↓
담보권 설정 확인
    ↓
여신계좌 생성 또는 활성화
    ↓
대출 실행 거래 생성
    ↓
대출금 지급
    ↓
대출잔액 반영
    ↓
상환 스케줄 생성
```

이때 중요한 것은 **대출 실행 거래의 정합성**이야.

예를 들어 대출금 지급에는 성공했지만 여신계좌 잔액 갱신에 실패하면 문제가 발생해.

따라서 다음 사항을 설계해야 해.

- 실행 요청의 멱등성 보장
- 중복 실행 방지
- 계좌 잔액과 거래 원장 정합성
- 실행 실패 시 재처리 및 대사
- 모든 실행 거래의 감사 이력 보관

### 상환 엔진

상환 기능은 기존 일반대출 모듈과 공통화하는 것을 추천해.

```java
public interface RepaymentCalculator {

    RepaymentSchedule calculate(
        BigDecimal principal,
        BigDecimal annualRate,
        int months
    );
}
```

구현체는 다음과 같이 분리할 수 있어.

```text
RepaymentCalculator
    │
    ├── EqualInstallmentCalculator
    │       원리금균등
    │
    ├── EqualPrincipalCalculator
    │       원금균등
    │
    └── BulletRepaymentCalculator
            만기일시
```

실제 상환 처리에서는 예정표 계산뿐 아니라 일할 이자, 금리 변경, 휴일 처리, 부분상환, 연체이자, 중도상환수수료 등을 별도로 다뤄야 해.

# 8. REST API 설계

프론트엔드와 연동할 API는 다음과 같이 구성하면 좋아.

| Method | Endpoint                                               | 기능             |
| ------ | ------------------------------------------------------ | ---------------- |
| POST   | `/api/v1/mortgages/applications`                       | 대출 신청        |
| GET    | `/api/v1/mortgages/applications/{id}`                  | 신청 조회        |
| POST   | `/api/v1/mortgages/applications/{id}/collaterals`      | 담보 등록        |
| POST   | `/api/v1/mortgages/applications/{id}/limits/calculate` | 한도 계산        |
| POST   | `/api/v1/mortgages/applications/{id}/screenings`       | 심사 요청        |
| GET    | `/api/v1/mortgages/applications/{id}/screenings`       | 심사 결과 조회   |
| POST   | `/api/v1/mortgages/applications/{id}/approvals`        | 승인 처리        |
| POST   | `/api/v1/mortgages/applications/{id}/agreements`       | 약정 등록        |
| POST   | `/api/v1/mortgages/applications/{id}/executions`       | 대출 실행        |
| GET    | `/api/v1/mortgages/accounts/{id}/repayments`           | 상환 스케줄 조회 |
| POST   | `/api/v1/mortgages/accounts/{id}/repayments`           | 대출 상환        |

승인 및 실행 API에는 반드시 권한 검증을 적용해야 해.

특히 대출 신청 고객이 직접 심사 승인이나 대출 실행을 호출할 수 없도록 역할을 분리해야 해.

# 9. bankEx 개발 로드맵

기존 프로젝트에 적용할 때는 아래 순서를 추천해.

| 단계   | 개발 범위              | 산출물                        |
| ------ | ---------------------- | ----------------------------- |
| 1단계  | 기존 여신 모듈 분석    | 재사용 기능 및 신규 기능 목록 |
| 2단계  | 주담대 DB 설계         | 테이블, 관계, 인덱스          |
| 3단계  | 대출 신청 및 담보 등록 | 신청 API 및 React 화면        |
| 4단계  | LTV·DTI·DSR 엔진       | 한도 계산 서비스 및 테스트    |
| 5단계  | 정책 관리              | 기준일별 규제 정책 엔진       |
| 6단계  | 여신 심사 및 승인      | 심사 워크플로                 |
| 7단계  | 대출 약정 및 실행      | 여신계좌 연계                 |
| 8단계  | 상환 및 이자 계산      | 상환 스케줄 및 거래 처리      |
| 9단계  | 예외 및 사후 관리      | 연체, 중도상환, 변경 처리     |
| 10단계 | 통합 테스트            | 전체 업무 시나리오 검증       |

## 10. 가장 중요한 설계 방향

이번 프로젝트에서는 다음 세 가지를 특히 중요하게 생각하면 좋아.

**첫째, 주담대와 일반대출의 공통 기능을 분리해야 해.** 고객 관리, 여신계좌, 상환, 이자 계산은 가능한 한 공통 모듈을 사용하고 주담대 특유의 담보 관리와 규제 심사만 별도로 구현하는 게 효율적이야.

**둘째, 계산 엔진과 심사 엔진을 분리해야 해.** LTV나 DSR 계산에 성공했다고 해서 자동으로 대출 승인이 되는 것은 아니야. 계산 결과는 심사 엔진의 입력값 중 하나로 사용해야 해.

**셋째, 정책과 거래 이력은 변경 가능성을 고려해야 해.** 규제 정책은 버전별로 관리하고, 승인·실행·상환 거래는 추적 가능한 형태로 보관해야 해.

### 최종 추천

현재 `bankEx`에는 일반대출, 전세대출, 여신 심사 등 관련 기능을 이미 설계하거나 개발해 온 이력이 있으므로, **주담대 기능을 별도 시스템으로 만들기보다는 기존 여신 시스템의 확장 상품으로 구현하는 방향**을 추천해.

특히 다음 구조가 적합해.

```text
bankEx
  │
  ├── 공통 여신 시스템
  │     ├── 고객 및 신용정보
  │     ├── 여신 심사
  │     ├── 여신계좌
  │     ├── 이자 계산
  │     └── 상환 관리
  │
  └── 대출상품
        ├── 일반 신용대출
        ├── 전세자금대출
        └── 주택담보대출
              ├── 담보 평가
              ├── 담보권 관리
              ├── LTV·DTI·DSR
              └── 주담대 규제 정책
```

**다음 개발 작업은 기존 `bankEx`의 여신 테이블과 서비스 구조를 확인한 뒤, 공통으로 재사용할 영역과 주담대 전용으로 구현할 영역을 구분하는 것**이야.

실제 프로젝트 코드를 확인하기 전까지는 위 구조를 권장 설계안으로 보는 것이 적절해.
