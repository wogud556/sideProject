# 가계대출 대환 업무 시스템 개발 명세서

## 1. 프로젝트 개요

은행의 **가계대출 대환 업무**를 처리하기 위한 웹 기반 업무 시스템을 개발한다.

본 시스템은 기존 금융기관 또는 동일 금융기관에서 보유하고 있는 가계대출을 조회하고, 대환 가능 여부를 판단한 뒤 신규 대출 실행 및 기존 대출 상환까지 처리하는 업무 흐름을 지원한다.

단순 CRUD 형태로 구현하지 말고 실제 은행 업무 시스템을 가정하여 다음을 중요하게 고려한다.

* 업무 프로세스 기반 화면 구성
* 단계별 업무 상태 관리
* 대출 원장 및 거래 이력 관리
* 대환 가능 여부 검증
* 기존 대출 상환 예정금액 조회
* 신규 대출 실행
* 기존 대출 상환
* 업무 실패 및 재처리
* 거래 정합성
* 감사 로그(Audit Log)
* 사용자 권한 관리
* 외부기관 연계 구조
* 장애 발생 시 롤백 및 재처리 구조

본 프로젝트는 실제 금융기관 연계 API가 없는 개발 환경에서도 실행 가능해야 한다.

따라서 외부기관 및 금융공동망 연계 부분은 반드시 Interface/Adapter 구조로 분리하고 Mock 구현체를 제공한다.

# 2. 기술 스택

## Frontend

* React
* TypeScript 사용 권장
* React Router
* Axios 또는 Fetch 기반 API Client
* React Query 또는 이에 준하는 서버 상태 관리 방식 권장
* 상태 관리가 필요한 경우 Zustand 또는 Redux Toolkit 사용 가능

UI Framework는 프로젝트에 기존 사용 중인 라이브러리가 있다면 해당 라이브러리를 우선 사용한다.

기존 프로젝트 구조와 코딩 컨벤션이 존재하면 이를 최우선으로 따른다.

---

## Backend

* Java
* Spring Boot
* Spring Web
* Spring Validation
* Spring Security
* Spring Transaction
* JPA 또는 MyBatis

DB 접근 기술은 기존 프로젝트에서 사용하는 기술을 우선 적용한다.

은행 업무 특성상 복잡한 조회 SQL이 필요한 경우 MyBatis 사용을 허용한다.

Service 계층에 SQL 또는 DB 종속 로직을 직접 작성하지 않는다.

---

## Database

Oracle Database를 기준으로 설계한다.

Oracle에서 정상적으로 실행 가능한 DDL 및 SQL을 작성한다.

다음을 고려한다.

* NUMBER
* VARCHAR2
* DATE / TIMESTAMP
* SEQUENCE
* INDEX
* PK / FK / UNIQUE
* 업무일자 기반 조회
* 대량 거래 조회 가능성

DB Object 이름은 일관된 Naming Convention을 적용한다.

```text
고객조회

 ↓
대환대상대출선택
 ↓
대환가능여부검증

 ↓

 ↓

 ↓
```

# 4. 업무 상태 정의

대환 신청 상태는 최소 다음 상태를 관리한다.

```text
DRAFT
작성중

REQUESTED
신청완료

REVIEWING
심사중

APPROVED
승인완료

REJECTED
승인거절

EXECUTING
대환실행중

NEW_LOAN_EXECUTED
신규대출실행완료

REPAYING
기존대출상환중

COMPLETED
대환완료

FAILED
처리실패

CANCELLED
취소
```

상태 변경은 Service 계층에서 통제한다.

Frontend가 상태값을 직접 변경하는 구조로 구현하지 않는다.

예:

```text
REQUESTED → REVIEWING
REVIEWING → APPROVED
REVIEWING → REJECTED
APPROVED → EXECUTING
EXECUTING → NEW_LOAN_EXECUTED
NEW_LOAN_EXECUTED → REPAYING
REPAYING → COMPLETED
```

허용되지 않은 상태 변경 요청은 Business Exception으로 처리한다.

# 7. 대환 대상 대출 선택

대출 목록에서 대환할 대출을 선택한다.

초기 버전에서는 단일 대출 대환을 기본으로 구현하되 향후 여러 개의 대출을 하나의 대출로 통합하는 형태가 가능하도록 데이터 모델을 설계한다.

즉,

```text
대환신청 1
   ↓
대환대상대출 N
```

구조를 사용한다.

---

# 8. 대환 가능 여부 검증

대환 신청 전에 반드시 대환 가능 여부를 검증한다.

검증 항목 예시는 다음과 같다.

* 대출 정상 여부
* 대출 잔액 존재 여부
* 연체 여부
* 이미 진행 중인 대환 신청 존재 여부
* 상환 제한 여부
* 대출 만기 여부
* 대상 상품 여부
* 고객 상태
* 신규대출 가능 한도
* 대환 신청 금액 적정성

검증 결과는 Boolean 하나로 반환하지 않는다.

다음과 같은 구조를 사용한다.

```json
{
  "eligible": false,
  "results": [
    {
      "code": "OVERDUE_LOAN",
      "passed": false,
      "message": "연체 중인 대출은 대환할 수 없습니다."
    }
  ]
}
```

Frontend에서는 검증 결과를 사용자가 확인할 수 있도록 표시한다.

# 9. 상환 예정금액 조회

기존 대출에 대해 기준일 현재 상환 예정금액을 계산 또는 조회한다.

구성 예:

```text
대출원금잔액
+ 당일까지 발생이자
+ 중도상환수수료
+ 기타비용
- 감면금액
----------------
= 최종상환예정금액
```

다음 항목을 반환한다.

* 원금잔액
* 발생이자
* 중도상환수수료
* 기타비용
* 감면금액
* 최종상환예정금액
* 산정기준일시

금액 계산은 Frontend에서 하지 않는다.

모든 금융 금액 계산은 Backend에서 수행한다.

Java에서는 금융 금액 및 금리 계산에 `double` 또는 `float`를 사용하지 말고 `BigDecimal`을 사용한다.

# 15. 신규대출 실행

신규대출 실행 시 외부 Core Banking 시스템과 연계한다고 가정한다.

직접 Service에 연계 로직을 구현하지 않는다.

다음 형태의 인터페이스를 설계한다.

```java
public interface LoanExecutionGateway {

    LoanExecutionResult executeLoan(
        LoanExecutionRequest request
    );

}
```

개발 환경에서는 다음 구현체를 제공한다.

```text
MockLoanExecutionGateway
```

향후 실제 시스템에서는

```text
CoreBankingLoanExecutionGateway
```

등으로 교체할 수 있도록 한다.

# 17. 매우 중요한 거래 정합성 처리

대환 업무에서 다음 상황을 반드시 고려한다.

```text
신규대출 실행 성공
+
기존대출 상환 실패
```

이 경우 단순 DB Transaction Rollback으로 해결할 수 없다.

이미 외부 시스템에서 신규대출이 실행되었기 때문이다.

따라서 업무 상태를 별도로 관리한다.

예:

```text
NEW_LOAN_EXECUTED
REPAYMENT_FAILED
```

그리고 재처리할 수 있도록 설계한다.

외부 거래와 내부 DB Transaction을 하나의 ACID Transaction으로 간주하지 않는다.

# 18. Idempotency

금융 거래 API는 중복 호출에 안전하도록 설계한다.

신규대출 실행 및 기존대출 상환 요청 시 각각 거래 고유번호를 사용한다.

예:

```text
transactionId
requestId
```

동일한 거래번호로 재요청할 경우 중복 금융거래가 발생하지 않도록 한다.

거래번호는 DB에 UNIQUE 제약조건을 설정한다.

# 22. 동시성 처리

같은 대환 신청에 대해 여러 사용자가 동시에 실행할 수 없도록 한다.

특히 다음 작업에 동시성 제어가 필요하다.

```text
승인
대출실행
상환
재처리
```

DB Lock 또는 Optimistic Lock을 적용한다.

JPA 사용 시 예:

```text
@Version
```

등을 고려한다.

실행 업무에는 상태 조건 Update를 함께 사용하는 것도 고려한다.

# 37. 구현 원칙

다음 원칙을 반드시 지킨다.

### 1.

Controller에 Business Logic을 작성하지 않는다.

### 2.

금액 계산에 `double`, `float`를 사용하지 않는다.

`BigDecimal`을 사용한다.

### 3.

Frontend에서 계산한 금융 금액을 신뢰하지 않는다.

### 4.

외부 금융기관 연계를 Service에 하드코딩하지 않는다.

Gateway / Adapter로 분리한다.

### 5.

대출 실행 및 상환 API는 Idempotency를 보장한다.

### 6.

업무 상태 변경은 Domain 또는 Service에서 통제한다.

### 7.

DB Transaction과 외부 금융 Transaction이 동일하다고 가정하지 않는다.

### 8.

실패 거래는 반드시 재처리 가능한 구조로 만든다.

### 9.

중요 업무는 Audit Log를 기록한다.

### 10.

기존 프로젝트의 코드 스타일, 패키지 구조, 공통 Component 및 공통 API 구조가 존재한다면 이를 우선 재사용한다.

# 39. Claude 작업 방식 지시

개발을 시작하기 전에 현재 Repository를 먼저 분석한다.

다음을 먼저 파악한다.

```text
현재 디렉터리 구조
Frontend 구조
Backend 구조
사용 중인 라이브러리
DB 접근 방식
API Response 규격
Exception 처리 방식
공통 Component
Authentication / Authorization 구조
Naming Convention
```

이미 존재하는 구조를 무시하고 새 프로젝트를 임의로 만들지 않는다.

기존 코드와 최대한 동일한 패턴으로 구현한다.

구현 전 먼저 변경하거나 추가할 파일 목록과 구현 계획을 작성한 뒤 실제 코드를 수정한다.

불명확한 부분은 은행 업무 시스템에 적합한 보수적인 방향으로 설계하되 특정 은행의 내부 업무규칙을 임의로 사실처럼 만들어 넣지 않는다.

실제 금융공동망, 타행, 코어뱅킹 등의 전문 규격이 존재하지 않는 부분은 반드시 Mock / Interface 구조로 남긴다.

최종적으로 다음 업무가 하나의 End-to-End Flow로 실행되어야 한다.

```text
고객조회
→ 기존대출조회
→ 대환대상선택
→ 대환가능여부확인
→ 상환예정금액조회
→ 신규대출조건입력
→ 대환신청
→ 심사
→ 승인
→ 신규대출실행
→ 기존대출상환
→ 대환완료
```
