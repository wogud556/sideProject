구현 완료 리포트 (2026-07-12 — 수신입출금 계좌 해지 기능)

## 개요

수신(deposit) 업무에 입출금 계좌 해지 기능을 추가했다. 사용자가 이번 작업을 "planner 에이전트로 요구사항 분석 → developer 에이전트로 구현 → reviewer 에이전트로 코드 리뷰 → tester 에이전트로 테스트 작성/실행"의 4단계 서브에이전트 파이프라인으로 진행해달라고 명시적으로 요청해, 프로젝트에 정의돼 있는 `.claude/agents/PLANNER.md`, `DEVELOPER.md`, `REVIEWER.md`, `TESTER.md` 페르소나를 그 순서대로 호출해 작업했다.

작업 중 `.claude/agents/PLANNER.MD`, `DEVELOPER.MD`가 확장자 대소문자(`.MD`) 때문에 세션에 정상 등록되지 않은 것을 발견해 `.md`로 정정했다. 다만 이미 시작된 세션에는 즉시 반영되지 않아, 이번 회차의 planner/developer 단계는 내장 `Plan`/`general-purpose` 에이전트에 동일한 페르소나 지시문을 그대로 주입해 대체 수행했다(reviewer/tester는 원래 소문자 확장자라 정상 호출). 확장자 수정 자체는 파일시스템에 반영되어 있어 다음 세션부터는 `planner`/`developer` 이름으로 바로 호출 가능하다(실제로 이번 세션 도중 시스템이 재스캔되며 두 이름이 뒤늦게 사용 가능 목록에 나타나는 것을 확인했다).

## 1. 기획 (Planner)

### 조사한 현재 상태
- `deposit/general/controller/accountController.java`: 조회(GET) 2개, 개설(POST) 1개만 존재. 해지 엔드포인트 없음.
- `deposit/general/entity/AccountInfo.java`: `accountStatus`, `closedAt` 필드는 이미 있었지만 아무도 채우지 않는 상태(스키마만 준비돼 있던 미구현 기능).
- 참고 패턴: `deposit/savings/service/savingsCancelService.java`(적금 중도해지) — 상태검증 → 정산 → 지급 → 상태전이 구조를 참고하되, 일반 입출금 계좌는 적금처럼 "정산금을 받을 계좌"가 미리 등록돼 있지 않다는 차이를 확인.

### 정책 결정 (사용자 확인 완료)

| 결정 사항 | 채택안 | 근거 |
|---|---|---|
| 엔드포인트 | `POST /api/bank/user/accounts/{accountNumber}/close` | 일반 입출금 계좌는 "해지"보다 도메인 용어로 `close`가 자연스러움 |
| 잔액이 0원이 아닌 계좌 해지 요청 | 거부 (`ACCOUNT_BALANCE_NOT_ZERO`) | 자동 이체 대상 계좌를 새로 받는 범위 확장 없이, 기존 `withdrawApi`로 먼저 전액 출금 후 재시도하는 흐름으로 충분 |
| 마지막 남은 계좌 해지 | 허용 | 계좌 개수 제한 로직 없이 단순하게 구현 |
| 활성 대출이 연결된 계좌 해지 | 불가 (`ACCOUNT_HAS_ACTIVE_LOAN`) | 대출 실행/상환 계좌가 사라지면 안 되므로 |

### API 설계
- 요청 `AccountCloseRequest { userId }`
- 응답 `AccountCloseResponse { accountId, accountNumber, accountStatus, closedAt, message }`
- `AccountResponse`에 `accountStatus` 필드 추가 (프론트에서 해지 여부를 판별할 수 있도록)
- 신규 `ErrorCode` 3종: `ACCOUNT_ALREADY_CLOSED`, `ACCOUNT_BALANCE_NOT_ZERO`, `ACCOUNT_HAS_ACTIVE_LOAN`
- 계좌 소유자(userId) 불일치 시에도 `ACCOUNT_NOT_FOUND`로 응답 (계좌 존재 여부 비노출)

### 테스트 전략 (요약)
정상 해지, 잔액 존재 시 거부, 출금 후 재시도 성공, 재해지 거부, 존재하지 않는 계좌, 소유자 불일치, 해지 후 입출금 회귀 확인, 해지 후 목록 조회 시 상태 유지, 활성 대출 보유 시 거부, 대출 전액상환 후 해지 가능 — 총 10개 시나리오를 도출.

## 3. 코드 리뷰 (Reviewer) 및 후속 조치

| 등급 | 내용 | 조치 |
|---|---|---|
| Critical | 요청 바디의 `userId`가 인증되지 않은 클라이언트 입력값이라, 계좌번호와 피해자 userId만 알면 누구나 타인의 계좌를 해지시킬 수 있음. 프로젝트 전체에 인증/세션 체계가 없어서 생기는 구조적 문제 | **의도적으로 스코프 밖으로 남김** (사용자 확인). 이번 기능만으로 해결할 수 없는 전사적 이슈로 별도 과제화 필요 |
| Major | 잔액 0원 확인과 상태를 CLOSED로 바꾸는 시점 사이에 락이 없어, 그 사이 동시 입금이 들어오면 잔액이 CLOSED 계좌에 영구히 묶이는 레이스 컨디션 발생 가능 | **수정**: `AccountInfoRepository`에 `findByAccountNumberForUpdate()`(`@Lock(PESSIMISTIC_WRITE)`) 추가, `closeAccount()`에서만 사용. 기존 입출금 흐름은 건드리지 않음 |
| Major | `accountService`가 `loan.general.mapper.LoanApplicationMapper`를 직접 주입받아 대출 상태 문자열("심사중"/"승인"/"실행완료")을 하드코딩 — deposit↔loan 도메인 양방향 의존 + 상태값 중복 | **수정**: `loanService`에 `hasActiveLoan(userId, accountNumber)` 공개 메서드를 신설해 판정 로직을 loan 도메인 내부로 이동. `accountService`는 매퍼 대신 `loanService`를 통해서만 조회하도록 변경 |
| Minor | 활성 대출 판정 시 검증된 `account.getUserId()` 대신 신뢰할 수 없는 `request.getUserId()`를 재사용 | 위 Major 리팩토링에 포함해 함께 수정 |
| Minor | `LoanApplicationMapper.findByUserId()` 전체 조회 후 애플리케이션 레벨 필터링(계좌번호 기준 전용 쿼리 없음), `MyPage.tsx`가 해지된 계좌를 구분 표시하지 않음, 도달 불가능한 상태 분기(현재는 ACTIVE/CLOSED 두 값뿐) 등 | 이번 스코프에서는 보류 (지적 사항으로만 기록) |

수정 반영 후 재컴파일(`./gradlew compileJava compileTestJava`)로 회귀 여부를 확인했다.

## 4. 테스트 (Tester)

신규 파일 `src/test/java/com/hanati/bank/bankEx/AccountCloseFlowTests.java`를 기존 `BankingFlowTests.java`와 동일한 스타일(`@SpringBootTest @Transactional`, 서비스 빈 직접 주입, `assertThrows` + `ErrorCode` 비교)로 작성했다.

### 테스트 시나리오 (10건, 전부 통과)
1. 잔액 0원 계좌 정상 해지
2. 잔액이 있는 계좌 해지 시도 → `ACCOUNT_BALANCE_NOT_ZERO`
3. 입금 후 동일 금액 출금(잔액 0 복귀) → 해지 성공
4. 이미 해지된 계좌 재해지 시도 → `ACCOUNT_ALREADY_CLOSED`
5. 존재하지 않는 계좌 해지 시도 → `ACCOUNT_NOT_FOUND`
6. 소유자 불일치 해지 시도 → `ACCOUNT_NOT_FOUND`
7. 해지된 계좌에 입금/출금 시도 → 기존 `ACCOUNT_NOT_ACTIVE` 가드로 회귀 확인
8. 해지 후 `getAccounts()` 조회 시 계좌가 사라지지 않고 `CLOSED` 상태로 유지
9. 활성 대출("심사중") 보유 계좌 해지 시도 → `ACCOUNT_HAS_ACTIVE_LOAN`
10. 대출 신청→승인→실행→전액상환 완료(잔여 0) 후에는 해지 가능

### 실행 결과
- `./gradlew test --tests "*AccountCloseFlowTests*"`: 10/10 통과
- `./gradlew test --rerun-tasks`(전체 스위트): **50개 테스트 전부 통과, 실패 0건**
  - `AccountCloseFlowTests` 10/10, `BankingFlowTests` 8/8(기존 `AccountResponse` 5-필드 생성자와 충돌 없음), `BankExApplicationTests` 1/1, `SavingsFlowTests` 8/8, `SavingsInterestServiceTest` 7/7, `JeonseLoanFlowTests` 9/9, `JeonseLimitCalculatorTest` 4/4, `JeonseRateCalculatorTest` 3/3
- 참고: 로컬 프로필(`application-local.yml`)이 Oracle이 아닌 인메모리 H2를 사용하도록 되어 있어 별도 DB 기동 없이 테스트가 수행됐다.
- 구현(프로덕션) 코드에서 별도 버그는 발견되지 않았다.

## 알려진 제한사항 / 다음 단계

1. **인증 부재**: 이번 기능을 포함해 프로젝트 전체 API가 클라이언트가 보낸 `userId`를 그대로 신뢰한다. 계좌 해지처럼 되돌릴 수 없는(destructive) 작업에서 특히 리스크가 크므로, 세션/토큰 기반 인증 도입을 후속 과제로 남긴다.
2. `MyPage.tsx`는 이번 스코프에서 건드리지 않아 계좌 목록에서 해지된 계좌가 활성 계좌와 구분 없이 표시된다. 필요 시 배지 표시나 목록 필터링 추가 검토.
3. 브라우저 수동 클릭 테스트는 자동화 도구가 없어 진행하지 못했다 — 사용자가 직접 확인 권장.
4. 변경사항은 커밋하지 않았다(사용자 요청).

## 기타 작업: `loan` → `bankEx` 최상위 폴더명 변경

여신뿐 아니라 수신 업무도 개발 중이라 최상위 개발 폴더명이 실제 범위와 맞지 않는다는 사용자 지적에 따라, `loan/`(레포지토리 루트 하위) 폴더를 `bankEx/`로 이름을 바꿨다.

- `git mv loan bankEx`로 히스토리를 보존하며 171개 파일 이동 (`bankEx/backend/bankEx/`, `bankEx/front/bankEx_Front/`)
- `CLAUDE.md`의 경로 참조 3곳(Frontend/Backend 커맨드 섹션, `application.yml` 설정 경로) 업데이트
- `loanController`, `/api/bank/user/loan/*` 같은 업무 도메인 이름(실제 "여신" 업무를 가리킴)은 그대로 유지 — 최상위 폴더명과는 무관한 이름이므로 손대지 않음
- `report/*.md` 등 과거 작업 기록 문서는 특정 시점의 기록이라 소급 수정하지 않음
