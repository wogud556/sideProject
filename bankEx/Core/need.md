있어. 은행 앱의 “대출 신청 화면”과 별개로, **실제 대출 계좌·잔액·이자·상환을 관리하는 대출 코어**라면 반드시 개발해야 하는 기본 업무가 있어.

핵심은 다음 흐름이야.

```text
상품 등록
  → 신청·심사
  → 승인
  → 약정
  → 대출 실행
  → 이자 계산
  → 원리금 상환
  → 연체 관리
  → 완제·해지
```

## 대출 코어의 기본 업무

### 1. 대출상품 관리

상품별 계산 규칙과 취급 조건을 관리하는 영역이야.

- 상품 코드와 상품명
- 신용대출·담보대출·한도대출 구분
- 최소·최대 대출금액
- 대출 기간
- 고정금리·변동금리
- 기준금리와 가산금리
- 상환 방식
- 거치기간
- 중도상환수수료 규칙
- 연체이율
- 취급 가능 고객 조건
- 상품 판매 시작·종료일
- 상품 규칙 버전 관리

중요한 점은 **대출이 실행될 때 적용된 상품 조건을 별도로 확정해 저장**하는 거야. 나중에 상품 금리가 바뀌더라도 이미 실행된 대출의 약정 조건이 함께 바뀌면 안 돼.

### 2. 신청·심사·승인

앱에서 신청 정보를 받는 부분이 아니라, 코어에서 실제 취급 가능 여부를 판단하고 승인 결과를 보관하는 업무야.

- 대출 신청 접수
- 고객·소득·부채 정보 저장
- 기존 대출 및 연체 여부 확인
- 한도 계산
- DSR 등 상환능력 평가
- 담보·보증 평가
- 금리 산정
- 자동 승인·수동 심사
- 승인·거절·조건부 승인
- 승인 유효기간
- 심사자와 승인자 분리
- 심사 근거와 변경 이력 보관

은행 감독 기준에서도 신용공여 한도와 상환능력 평가가 중요한 관리 대상이므로, 단순히 `approved = true`만 저장하지 말고 **심사 당시 입력값·산출값·규칙 버전**을 같이 남기는 편이 좋아. [은행업감독규정](https://www.law.go.kr/LSW/admRulLsInfoP.do?admRulSeq=2100000210972)

### 3. 약정 관리

승인 결과를 실제 계약 조건으로 확정하는 단계야.

- 약정번호 생성
- 승인금액과 약정금액 확정
- 약정금리
- 만기일
- 상환 방식
- 상환일
- 출금계좌·입금계좌
- 담보·보증 연결
- 계약 상태 관리
- 약정 변경 이력
- 철회·취소 처리

대출계약 철회는 일반 중도상환과 처리 결과가 다를 수 있으므로 별도의 업무 유형으로 모델링하는 게 안전해. 금융위원회 설명상 적용 대상 거래에서는 철회 시 원리금 반환, 수수료 면제 및 관련 대출정보 삭제 절차가 발생한다. [금융위원회 대출계약 철회권 안내](https://www.fsc.go.kr/no010101/72189)

### 4. 대출 실행

승인된 대출을 실제 계좌로 만들고 돈을 지급하는 업무야.

- 대출계좌번호 생성
- 실행 가능 상태 검증
- 승인·약정 금액과 실행 금액 비교
- 고객 계좌 입금
- 기존 대출 상환 계좌로 직접 지급
- 분할 실행
- 실행 취소 및 당일 취소
- 회계 거래 생성
- 중복 실행 방지

여기서는 반드시 **멱등성 키**가 필요해. 네트워크 재시도로 동일 요청이 두 번 들어와도 대출이 두 번 실행되면 안 돼.

### 5. 대출 원장 관리

대출 코어에서 가장 중요한 부분이야.

최소한 다음 금액을 분리해야 해.

- 최초 대출원금
- 현재 원금잔액
- 정상 이자
- 미수 이자
- 연체 이자
- 수수료
- 연체 원금
- 상환 예정 금액
- 실제 상환 금액
- 면제·감면 금액

단순히 `loan.balance` 하나만 수정하기보다 모든 거래를 원장에 남기는 편이 좋아.

```text
대출실행       +100,000,000
원금상환        -1,000,000
원금상환취소    +1,000,000
중도상환       -10,000,000
```

현재 잔액은 원장 거래의 결과로 계산되고, 별도의 잔액 테이블은 조회 성능을 위한 집계값으로 운영하는 구조가 안정적이야.

### 6. 금리·이자 계산

- 고정금리
- 변동금리
- 기준금리 변경
- 가산·우대금리
- 일수 계산 기준
- 윤년 처리
- 이자 계산 시작일·종료일
- 원 미만 절사·반올림
- 정상 이자
- 연체 이자
- 이자 감면
- 일별 이자 발생 처리

예를 들어 금리는 하나의 숫자보다 구성 요소로 보관하는 게 좋아.

```text
적용금리 = 기준금리 + 가산금리 - 우대금리
```

변동금리 대출은 기준금리 변경 이력과 다음 금리 변경일도 필요해.

### 7. 상환 스케줄 생성

- 만기일시상환
- 원금균등상환
- 원리금균등상환
- 거치 후 분할상환
- 수시상환
- 상환일이 휴일인 경우 처리
- 첫 회차·마지막 회차 금액 보정
- 금리 변경 이후 스케줄 재산정

스케줄에는 최소한 아래 항목이 필요해.

```text
회차
납부예정일
기초원금
예정원금
예정이자
예정수수료
납부금액
납부상태
납부일
```

### 8. 원리금 상환

- 정기 상환
- 자동이체
- 수동 납부
- 부분 상환
- 중도상환
- 전액 상환
- 상환 취소
- 과오납 환급
- 상환금 배분

상환금 배분 순서는 매우 중요해. 예를 들어 다음처럼 상품 규칙으로 관리해야 해.

```text
비용 → 연체이자 → 정상 이자 → 연체원금 → 정상원금
```

코드에 순서를 고정하기보다 `RepaymentAllocationPolicy` 같은 정책 객체로 분리하는 게 좋아.

### 9. 연체·기한이익상실

- 납부일 미납 판정
- 연체 시작일 기록
- 연체 원금 분리
- 연체 이자 계산
- 연체 단계 관리
- 독촉·추심 상태
- 기한이익상실
- 회수·상각
- 정상화
- 연체 취소 및 소급 정정

상태는 단순한 `OVERDUE` 하나보다 단계별로 관리해야 해.

```text
NORMAL
→ PAST_DUE
→ DELINQUENT
→ ACCELERATED
→ WRITTEN_OFF
→ RECOVERED
```

### 10. 만기·완제·해지

- 만기 도래
- 만기 연장
- 조건 변경
- 전액 상환 금액 조회
- 완제 처리
- 대출계좌 종료
- 담보·보증 해제
- 완제 취소
- 완제증명 데이터 생성

원금만 0원이 됐다고 완제하면 안 되고, 이자·연체이자·수수료·미처리 거래까지 모두 확인해야 해.

### 11. 회계·배치·대사

실제 코어다운 시스템을 만들려면 이 부분이 필요해.

- 대출 실행 분개
- 원금 회수 분개
- 이자 수익 인식
- 미수이자 계상
- 연체·상각 분개
- 일 마감
- 월 마감
- 이자 일괄 계산
- 납부 예정 생성
- 자동이체 요청
- 원장과 회계 잔액 대사
- 실패 배치 재처리

```text
대출 업무 거래
   ↓
대출 원장
   ↓
회계 이벤트
   ↓
회계 분개
   ↓
일 마감 대사
```

### 12. 통제와 감사

- 업무 권한 분리
- 승인자·실행자 분리
- 모든 변경 이력
- 거래 전후 값 기록
- 취소 대신 역거래 사용
- 중복 거래 방지
- 개인정보 마스킹
- 배치 재실행 안전성
- 업무일자와 시스템 일자 분리

은행 코어에서는 삭제보다 **취소 거래 또는 반대 방향의 역거래**를 생성하는 방식이 적합해. 그래야 당시 잔액과 처리 이력을 다시 재현할 수 있어.

## 네 프로젝트에서 먼저 구현할 범위

포트폴리오용 대출 코어라면 아래 순서가 적당해.

1. 대출상품 및 금리 규칙
2. 대출 신청·승인
3. 약정 및 실행
4. 대출계좌와 거래원장
5. 상환 스케줄 생성
6. 정상 원리금 상환
7. 중도상환 및 전액상환
8. 일별 이자 계산
9. 연체 전환 및 연체이자
10. 거래 취소·역거래
11. 일 마감 및 잔액 대사
12. 감사 로그

특히 **대출 원장, 이자 계산, 상환금 배분, 취소·역거래, 일 마감 대사**까지 구현하면 단순 은행 앱이 아니라 “대출 코어 업무를 이해하고 만든 프로젝트”라는 성격이 분명해져.

추천 패키지 구조는 다음과 같아.

```text
loan/
├── product/          # 상품과 금리 규칙
├── origination/      # 신청·심사·승인
├── agreement/        # 약정
├── account/          # 대출계좌와 잔액
├── disbursement/     # 실행
├── interest/         # 이자 계산
├── schedule/         # 상환 스케줄
├── repayment/        # 원리금 상환
├── delinquency/      # 연체
├── collateral/       # 담보·보증
├── accounting/       # 회계 이벤트·분개
├── batch/            # 일 마감·월 마감
└── audit/            # 감사·변경 이력
```

현재 `loan/general`, `loan/jeonse`처럼 상품 종류를 최상위로 나누기보다, **공통 대출 코어를 먼저 만들고 일반대출·전세대출은 상품별 정책을 주입하는 구조**가 장기적으로 더 적합해.
