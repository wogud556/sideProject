5. 주요 업무 규칙

계좌 검증

* 출금계좌와 수취계좌가 존재해야 한다.
* 출금계좌는 로그인한 고객의 계좌여야 한다.
* 출금계좌와 수취계좌는 입출금이 가능한 계좌여야 한다.
* 해지, 휴면, 거래정지 계좌는 이체할 수 없다.
* 출금계좌와 수취계좌가 동일하면 이체할 수 없다.

금액 검증

* 이체금액은 0원보다 커야 한다.
* 이체금액은 출금계좌의 출금 가능 잔액 이하여야 한다.
* 1회 이체한도를 초과할 수 없다.
* 1일 누적 이체한도를 초과할 수 없다.

비밀번호 검증

* 출금계좌 비밀번호가 일치해야 한다.
* 비밀번호 오류 횟수가 기준을 초과하면 계좌 거래를 제한한다.
* 간단한 프로젝트에서는 오류 횟수 제한 기능을 별도 범위로 분리할 수 있다.

트랜잭션 처리

아래 작업은 반드시 하나의 데이터베이스 트랜잭션으로 처리한다.

출금계좌 잔액 차감
입금계좌 잔액 증가
출금 거래내역 저장
입금 거래내역 저장
이체 원장 저장

하나라도 실패하면 전체 작업을 롤백해야 한다.

9. 서비스 처리 순서

TransferService.transfer()는 다음 순서로 구현한다.

1. requestId 중복 여부 확인
2. 출금계좌 조회 및 잠금
3. 입금계좌 조회 및 잠금
4. 출금계좌 소유 고객 확인
5. 계좌 상태 확인
6. 동일 계좌 여부 확인
7. 계좌 비밀번호 확인
8. 출금 가능 잔액 확인
9. 1회 및 1일 이체한도 확인
10. 이체 원장 PROCESSING 상태 생성
11. 출금계좌 잔액 차감
12. 출금 거래내역 생성
13. 입금계좌 잔액 증가
14. 입금 거래내역 생성
15. 이체 원장 COMPLETED 상태 변경
16. 이체 결과 반환

서비스 메서드에는 다음 트랜잭션 처리를 적용한다.

@Transactional
public TransferResponse transfer(TransferRequest request) {
    // 이체 처리
}

동시 출금으로 인한 잔액 오류를 방지하기 위해 출금계좌 조회 시 비관적 잠금 또는 낙관적 잠금을 적용한다.

예시:

SELECT *
FROM ACCOUNT
WHERE ACCOUNT_NUMBER = ?
FOR UPDATE;

10. 중복 이체 방지

프론트엔드 또는 호출 시스템에서 이체 요청마다 고유한 requestId를 생성한다.

동일한 requestId가 다시 요청되면 이체를 중복 실행하지 않고 기존 처리 결과를 반환한다.

REQUEST_ID UNIQUE 제약조건 적용

이는 사용자가 이체 버튼을 여러 번 누르거나 네트워크 재시도가 발생했을 때 중복 출금을 방지하기 위한 기능이다.

11. 오류 코드

오류 코드	설명
ACCOUNT_NOT_FOUND	계좌가 존재하지 않음
ACCOUNT_NOT_OWNED	본인 소유의 출금계좌가 아님
ACCOUNT_NOT_ACTIVE	정상 상태의 계좌가 아님
SAME_ACCOUNT_TRANSFER	동일 계좌 간 이체 요청
INVALID_ACCOUNT_PASSWORD	계좌 비밀번호 불일치
INVALID_TRANSFER_AMOUNT	이체금액 오류
INSUFFICIENT_BALANCE	잔액 부족
PER_TRANSFER_LIMIT_EXCEEDED	1회 이체한도 초과
DAILY_TRANSFER_LIMIT_EXCEEDED	1일 이체한도 초과
DUPLICATE_TRANSFER_REQUEST	중복 이체 요청
TRANSFER_PROCESSING_FAILED	이체 처리 중 오류

실패 테스트

* 존재하지 않는 출금계좌
* 존재하지 않는 수취계좌
* 본인 소유가 아닌 출금계좌

* 동일 계좌 이체
* 해지 계좌 이체

* 1회 이체한도 초과
* 1일 이체한도 초과
* 동일 requestId 재요청
* 거래내역 저장 실패 시 전체 롤백

동시성 테스트

동일 계좌에서 동시에 여러 이체 요청을 실행하더라도 계좌 잔액이 음수가 되거나 실제 잔액보다 많은 금액이 출금되지 않아야 한다.
