은행 기본 업무 개발 명세서

신규 가입고객 등록, 수신 업무, 여신 업무 연계

1. 개발 목적

현재 개발되어 있는 여신 업무 시스템과 연계할 수 있도록, 은행 업무의 가장 기본이 되는 다음 기능을 백엔드 중심으로 구현한다.

* 신규 가입 고객 등록
* 고객 기본정보 관리
* 수신 계좌 개설
* 입금, 출금, 계좌 조회
* 계좌 상태 관리
* 수신 계좌와 기존 여신 업무 연계
* 대출 신청 시 고객 및 계좌 검증

본 프로젝트는 실제 은행 시스템의 복잡한 전문, 대외계, 인증, 심사 자동화 전체를 구현하는 것이 아니라, 학습 및 사이드 프로젝트 수준에서 은행 핵심 프로세스를 이해할 수 있는 구조로 구현한다.

⸻

2. 전체 업무 흐름

2.1 신규 고객 등록 흐름

1. 사용자가 회원가입 정보를 입력한다.
2. 고객 기본정보를 등록한다.
3. 중복 고객 여부를 확인한다.
4. 고객번호를 생성한다.
5. 로그인 정보를 생성한다.
6. 기본 고객 상태를 ACTIVE로 저장한다.
7. 이후 수신 계좌 개설 및 여신 신청에서 해당 고객 정보를 사용한다.

⸻

2.2 수신 계좌 개설 흐름

1. 고객이 계좌 개설을 요청한다.
2. 고객 존재 여부를 확인한다.
3. 고객 상태가 정상인지 확인한다.
4. 계좌번호를 난수 또는 규칙 기반으로 생성한다.
5. 수신 계좌 정보를 저장한다.
6. 초기 잔액은 0원으로 생성한다.
7. 계좌 상태는 ACTIVE로 생성한다.

⸻

2.3 입금 흐름

1. 계좌번호로 계좌를 조회한다.
2. 계좌 상태가 정상인지 확인한다.
3. 입금 금액이 0보다 큰지 검증한다.
4. 계좌 잔액을 증가시킨다.
5. 거래내역을 저장한다.

⸻

2.4 출금 흐름

1. 계좌번호로 계좌를 조회한다.
2. 계좌 상태가 정상인지 확인한다.
3. 출금 금액이 0보다 큰지 검증한다.
4. 잔액이 출금 금액보다 크거나 같은지 확인한다.
5. 계좌 잔액을 차감한다.
6. 거래내역을 저장한다.

⸻

2.5 여신 업무 연계 흐름

기존 여신 업무에서 대출 신청을 받을 때 다음 정보를 연계한다.

1. 고객번호 기준으로 고객 정보를 조회한다.
2. 고객 상태가 정상인지 확인한다.
3. 고객의 대표 수신 계좌를 조회한다.
4. 대출 실행 계좌로 사용할 수 있는지 검증한다.
5. 대출 승인 후 실행 금액을 해당 수신 계좌에 입금한다.
6. 거래내역에는 LOAN_DISBURSEMENT 유형으로 기록한다.

⸻

3. 주요 도메인

3.1 고객

고객은 은행 업무의 기준이 되는 주체이다.

주요 속성:

* 고객 ID
* 고객번호
* 이름
* 생년월일
* 휴대폰 번호
* 이메일
* 주소
* 고객 상태
* 가입일시
* 수정일시

고객 상태:

* ACTIVE: 정상
* INACTIVE: 비활성
* BLOCKED: 거래 제한
* WITHDRAWN: 탈퇴

⸻

3.2 로그인 정보

로그인 정보는 고객의 인증용 정보이다.

주요 속성:

* 로그인 ID
* 고객 ID
* 사용자 ID
* 비밀번호
* 로그인 상태
* 마지막 로그인 일시
* 마지막 로그아웃 일시

비밀번호 암호화는 현재 프로젝트 범위에서는 제외해도 된다. 단, 구조상 추후 암호화 적용이 가능하도록 서비스 계층에서 처리한다.

⸻

3.3 수신 계좌

수신 계좌는 고객의 예금 계좌이다.

주요 속성:

* 계좌 ID
* 계좌번호
* 고객 ID
* 상품 코드
* 계좌명
* 잔액
* 계좌 상태
* 개설일시
* 해지일시

계좌 상태:

* ACTIVE: 정상
* SUSPENDED: 거래정지
* CLOSED: 해지

⸻

3.4 수신 거래내역

입금, 출금, 대출 실행금 입금 등 모든 계좌 거래를 기록한다.

거래 유형:

* DEPOSIT: 입금
* WITHDRAW: 출금
* TRANSFER_IN: 이체 입금
* TRANSFER_OUT: 이체 출금
* LOAN_DISBURSEMENT: 대출 실행금 입금
* LOAN_REPAYMENT: 대출 상환 출금

⸻

ALTER TABLE LOAN_APPLICATION

6. 여신 업무 연계 API

6.1 대출 신청 전 고객 및 계좌 검증 API

GET /api/loan/validate-customer-account

Query Parameters:

customerId=1
accountNo=100200300001

Response:

{
  "valid": true,
  "customerId": 1,
  "accountNo": "100200300001",
  "message": "대출 신청 가능한 고객 및 계좌입니다."
}

검증 조건:

* 고객이 존재해야 한다.
* 고객 상태가 ACTIVE여야 한다.
* 계좌가 존재해야 한다.
* 계좌의 고객 ID와 요청 고객 ID가 일치해야 한다.
* 계좌 상태가 ACTIVE여야 한다.

⸻

6.2 대출 실행금 입금 API

POST /api/loan/disbursement

Request:

{
  "loanApplicationId": 1,
  "customerId": 1,
  "disbursementAccountNo": "100200300001",
  "loanAmount": 10000000
}

Response:

{
  "loanApplicationId": 1,
  "customerId": 1,
  "disbursementAccountNo": "100200300001",
  "loanAmount": 10000000,
  "transactionType": "LOAN_DISBURSEMENT",
  "message": "대출 실행금 입금이 완료되었습니다."
}

처리 흐름:

1. 대출 신청 정보를 조회한다.
2. 대출 승인 상태인지 확인한다.
3. 고객 상태를 확인한다.
4. 실행 계좌가 고객 소유인지 확인한다.
5. 실행 계좌 상태가 정상인지 확인한다.
6. 수신 계좌 잔액을 대출금만큼 증가시킨다.
7. 수신 거래내역에 LOAN_DISBURSEMENT를 저장한다.
8. 대출 신청 또는 대출 계좌 상태를 EXECUTED로 변경한다.

⸻

POST /api/loan/repayment

Request:

{
  "loanAccountId": 1,
  "customerId": 1,
  "repaymentAccountNo": "100200300001",
  "repaymentAmount": 300000
}

Response:

{
  "loanAccountId": 1,
  "customerId": 1,
  "repaymentAccountNo": "100200300001",
  "repaymentAmount": 300000,
  "transactionType": "LOAN_REPAYMENT",
  "message": "대출 상환이 완료되었습니다."
}

처리 흐름:

1. 대출 계좌를 조회한다.
2. 고객 상태를 확인한다.
3. 상환 계좌가 고객 소유인지 확인한다.
4. 상환 계좌 잔액이 충분한지 확인한다.
5. 수신 계좌 잔액을 차감한다.
6. 수신 거래내역에 LOAN_REPAYMENT를 저장한다.
7. 여신 상환내역을 저장한다.
8. 대출 잔액을 차감한다.

9. 트랜잭션 처리 기준

다음 업무는 반드시 트랜잭션으로 처리한다.

12. 개발 요청사항

Claude Code는 다음 기준으로 개발을 진행한다.

1. 기존 프로젝트 구조를 먼저 분석한다.
2. 현재 존재하는 여신 업무 도메인, 테이블, API를 확인한다.
3. 기존 스타일에 맞춰 신규 고객, 로그인, 수신 업무 패키지를 추가한다.
4. Controller, Service, Mapper, DTO, Domain 계층을 분리한다.
5. DB는 기존 프로젝트가 사용하는 방식에 맞춘다.
    * MyBatis 사용 시 Mapper XML 작성
    * JPA 사용 시 Entity/Repository 작성
6. 수신 업무의 입금, 출금, 대출 실행, 상환 처리는 반드시 트랜잭션으로 묶는다.
7. 기존 여신 업무와 직접 결합하지 않고, LoanLinkService 또는 별도 연계 서비스로 느슨하게 연결한다.
8. 테스트 가능한 단위로 구현한다.
9. API 요청/응답 JSON 예시와 Postman 테스트 순서를 함께 작성한다.
10. 컴파일 오류가 없도록 전체 프로젝트 기준으로 빌드 검증한다.
