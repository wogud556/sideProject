네. 현재 기준으로 비교하면 **Qwen 3.6은 비용·통제권·로컬 실행**, Claude의 최신 상위 모델은 **판단력·지시 준수·장시간 작업의 안정성** 쪽에 무게가 있다고 보는 게 실용적입니다.

다만 주의할 점이 하나 있습니다. Qwen이 공개한 비교표는 주로 **Claude Opus 4.5**를 대상으로 합니다. 현재 Claude 상위 제품은 **Opus 5**까지 나왔으므로, Qwen 공식 벤치마크만 보고 “Qwen 3.6이 최신 Claude보다 우수하다”고 결론 내리면 안 됩니다. [Claude Opus 공식 정보](https://www.anthropic.com/claude/opus)

### Qwen 3.6을 쓸 때 특히 유의할 점

1. **“작업 완료”라는 말을 그대로 믿지 마세요.**

코딩 에이전트는 테스트를 실제로 실행하지 않았거나, 오류가 남았는데도 완료했다고 보고할 수 있습니다. 항상 다음을 명시하는 게 좋습니다.

> 변경 후 테스트·린트·빌드를 실행하고, 실행한 명령과 종료 코드를 보고하라. 실행하지 못한 검증은 완료했다고 표현하지 마라.

Claude에도 필요한 원칙이지만, Qwen으로 자동화를 구성할 때는 특히 중요합니다.

2. **큰 작업을 한 번에 맡기지 마세요.**

저장소 전체를 바로 수정하게 하기보다는 다음 순서가 안전합니다.

- 먼저 구조와 문제 원인 분석
- 수정 계획과 대상 파일 제시
- 작은 단위로 구현
- 테스트 실행
- 마지막에 diff와 위험 요소 검토

Qwen의 26만~101만 토큰 문맥은 “많이 넣을 수 있다”는 뜻이지, 모든 내용을 빠짐없이 정확하게 활용한다는 뜻은 아닙니다.

3. **Claude보다 요구사항을 더 명시적으로 작성하세요.**

Claude 최신 상위 모델은 모호한 요구에서 전제나 위험을 먼저 지적하는 경향을 강조합니다. Qwen에는 다음 내용을 구체적으로 주는 것이 안전합니다.

- 수정 가능한 파일
- 수정하면 안 되는 부분
- 성공 조건
- 호환해야 할 버전
- 테스트 명령
- 실패하면 멈춰야 하는 조건
- 삭제·배포·커밋 등에 필요한 승인 조건

예를 들어 “로그인 기능을 고쳐줘”보다 다음처럼 요청하는 편이 좋습니다.

> 원인을 먼저 분석하고 코드는 아직 변경하지 마라. 재현 테스트를 작성한 뒤 최소 수정안을 제시하라. DB 스키마와 공개 API는 변경하지 마라.

4. **터미널 권한은 제한하세요.**

Qwen Code나 자체 에이전트에 터미널을 연결할 경우:

- 기본적으로 읽기 전용으로 시작
- 삭제·배포·패키지 게시·마이그레이션은 승인 필수
- 비밀키와 `.env` 접근 차단
- 컨테이너나 별도 작업 트리에서 실행
- 명령 허용 목록 사용
- 변경 전후 `git diff` 확인

로컬 모델이라고 해서 명령 실행 자체가 안전해지는 것은 아닙니다. 데이터 유출 위험은 줄어들 수 있지만 잘못된 파일 수정이나 삭제 위험은 그대로입니다.

5. **Qwen의 ‘추론 보존’을 무조건 켜두지 마세요.**

이전 추론 문맥을 유지하면 반복 작업은 빨라지지만, 초기에 세운 잘못된 가정도 계속 이어질 수 있습니다. 요구사항이 바뀌거나 접근 방식이 틀렸다면 새 세션에서 다시 시작하거나 다음처럼 요청하는 것이 좋습니다.

> 기존 결론을 전제로 삼지 말고 원본 코드와 테스트 결과로부터 다시 검증하라.

6. **양자화 모델은 원본과 동일하지 않습니다.**

로컬에서 4비트나 저비트 GGUF를 사용하면 메모리를 절약할 수 있지만, 복잡한 추론·도구 호출 형식·긴 문맥에서 품질이 떨어질 수 있습니다. 중요한 코드 작업이라면:

- 작은 수정은 양자화 Qwen
- 어려운 설계와 최종 리뷰는 원본 API 또는 Claude
- 같은 내부 평가 세트로 모델·양자화별 성공률 측정

방식이 현실적입니다.

### 추천 조합

개인 개발이나 비용을 중시한다면:

- 일상적인 코드 작성·반복 수정: **Qwen3.6-35B-A3B**
- 까다로운 버그·아키텍처·최종 검토: **Claude Opus**
- 민감한 사내 코드: **로컬 Qwen**
- 높은 신뢰성이 필요한 변경: 두 모델로 교차 검토

가장 좋은 운용 방식은 한 모델을 무조건 신뢰하는 것이 아니라, **Qwen이 구현하고 Claude가 반대 관점에서 리뷰하게 하거나 그 반대로 수행하는 것**입니다. 단, 두 모델이 같은 답을 내더라도 테스트와 보안 검토를 대신할 수는 없습니다.

요약하면, **Qwen 3.6은 직접 통제하고 저렴하게 많이 돌릴 때 매력적이고, Claude는 모호하고 복잡한 업무에서 감독 비용을 줄이는 쪽이 강점**입니다. Qwen 공식 자료에서도 코딩 에이전트와 추론 문맥 보존을 핵심 개선점으로 설명하고 있습니다. [Qwen3.6 공식 저장소](https://github.com/QwenLM/Qwen3.6)


로컬 LLM 세팅에서 가장 중요한 것은 **모델 이름보다 메모리 용량, 양자화, 컨텍스트 길이, 실행 프레임워크의 조합**입니다.

### 1. VRAM·통합 메모리가 최우선

모델이 메모리에 들어가야 제대로 실행됩니다.

대략적인 4비트 양자화 기준이며, 실행 오버헤드와 KV 캐시는 별도입니다.

| 모델 규모 | 최소 메모리 | 권장 메모리 |
| --------- | ----------: | ----------: |
| 7~9B      |       6~8GB |   12GB 이상 |
| 14B       |     10~12GB |   16GB 이상 |
| 27~35B    |     18~24GB |   32GB 이상 |
| 70B       |   40GB 전후 |   64GB 이상 |

Qwen3.6-35B-A3B는 한 번에 약 3B가 활성화되는 MoE 모델이지만, **전체 35B 가중치를 메모리 또는 저장장치에서 관리해야 합니다.** 따라서 3B 모델처럼 4~6GB에서 가볍게 돌아가는 모델은 아닙니다.

Apple Silicon은 VRAM 대신 통합 메모리를 사용합니다. macOS와 다른 앱도 같은 메모리를 사용하므로:

- 16GB: 7~9B 권장
- 24GB: 14B 또는 일부 27B 저비트
- 32~36GB: 27~35B 4비트 실용권
- 64GB 이상: 큰 모델과 긴 컨텍스트에 유리

정도로 생각하면 됩니다.

### 2. 양자화는 무조건 작을수록 좋은 게 아닙니다

일반적인 선택은 다음과 같습니다.

- **Q4_K_M·4비트:** 크기와 품질의 균형이 가장 좋음
- **Q5_K_M·5비트:** 코드·추론 품질을 조금 더 보존
- **Q6/Q8:** 메모리가 충분하고 정확도가 중요할 때
- **Q2/Q3:** 실행은 가능하지만 복잡한 추론과 도구 호출에서 성능 저하 가능

처음에는 Q4_K_M으로 시작하고, 중요한 코딩 작업에서 부족하면 Q5나 Q6로 올리는 것이 좋습니다.

### 3. 컨텍스트를 최대값으로 설정하지 마세요

Qwen3.6은 기본 262K, 확장 시 약 1M 토큰을 지원하지만, 로컬에서 최대값을 설정하면 KV 캐시가 커져 속도와 메모리 사용량이 급격히 증가합니다.

실용적인 시작값은:

- 일반 대화: 8K~16K
- 코딩: 16K~32K
- 중형 저장소 분석: 32K~64K
- 128K 이상: 실제 필요성과 메모리를 확인한 후 사용

입니다. 긴 문서를 전부 넣기보다 검색/RAG나 필요한 파일 선별이 효율적입니다.

### 4. 목적에 맞는 실행 프로그램을 선택하세요

- **Ollama:** 설치와 API 연결이 간편
- **LM Studio:** GUI로 모델을 시험하기 좋음
- **llama.cpp:** GGUF 세부 설정과 하드웨어 최적화에 유리
- **MLX:** Apple Silicon에서 좋은 선택
- **vLLM/SGLang:** NVIDIA GPU 서버와 여러 사용자 처리에 적합

Qwen3.6은 공식적으로 llama.cpp, MLX, vLLM, SGLang 등을 지원합니다. 다만 모델 출시 초기에는 도구 호출이나 채팅 템플릿 호환 문제가 있을 수 있으므로 최신 버전과 해당 모델 전용 템플릿을 사용해야 합니다. [Qwen3.6 공식 저장소](https://github.com/QwenLM/Qwen3.6)

### 5. CPU 오프로딩은 가능하지만 속도를 확인하세요

GPU 메모리가 부족하면 일부 레이어를 RAM으로 넘길 수 있습니다. 모델이 실행되기는 하지만 토큰 생성 속도가 크게 떨어질 수 있습니다.

확인할 지표는 다음 세 가지입니다.

- 첫 응답까지 걸리는 시간
- 초당 생성 토큰 수
- 프롬프트 처리 속도

긴 코드나 문서에서는 생성 속도보다 프롬프트 처리 시간이 더 큰 병목이 되기도 합니다.

### 6. 코딩용이라면 도구 호출부터 검증하세요

모델이 대화를 잘하는 것과 코딩 에이전트로 잘 작동하는 것은 다릅니다. 다음을 별도로 테스트해야 합니다.

- JSON 및 함수 호출 형식 준수
- 여러 번 연속 도구 호출
- 터미널 오류 인식
- 파일 수정 범위 준수
- 테스트·빌드 결과 확인
- 긴 작업에서 같은 행동을 반복하지 않는지

실행 프로그램이 모델의 채팅 템플릿과 reasoning parser를 제대로 지원하지 않으면 모델 성능과 무관하게 도구 호출이 깨질 수 있습니다.

### 7. 보안 설정

로컬 모델의 가장 큰 이점은 데이터 통제이지만, 다음 조건을 만족해야 실제로 로컬이라고 할 수 있습니다.

- 실행 프로그램의 텔레메트리 확인
- 외부 검색과 클라우드 fallback 비활성화
- API 서버는 기본적으로 `127.0.0.1`에만 바인딩
- 외부 공개 시 인증과 방화벽 적용
- `.env`, SSH 키, 비밀번호 저장소 접근 제한
- 코딩 에이전트는 별도 Git 작업 트리나 컨테이너에서 실행
- 삭제·배포·커밋·패키지 게시 명령은 승인받도록 설정

### 추천 시작 구성

개인용으로 무난한 구성은 다음과 같습니다.

- 모델: 하드웨어에 맞는 Qwen 7~35B
- 양자화: Q4_K_M
- 컨텍스트: 16K 또는 32K
- 온도: 코딩 0.1~0.3, 대화 0.6~0.8
- 실행기: Mac은 MLX/llama.cpp, 간편 사용은 Ollama/LM Studio
- API: localhost 전용
- 검증: 본인이 자주 쓰는 질문과 코드 작업 20개로 모델 비교

결론적으로 **최대 모델을 억지로 실행하는 것보다, 여유 있게 돌아가는 작은 모델을 충분한 컨텍스트와 안정적인 양자화로 사용하는 편이 실제 체감이 좋습니다.**


아니요. **기본 원리는 비슷하지만, 모든 LLM에 동일한 설정을 그대로 적용하면 안 됩니다.** 모델마다 구조, 파일 형식, 채팅 규칙, 추론 방식이 다르기 때문입니다.

쉽게 말하면:

- 공통 부분: 하드웨어·메모리·서버 설정
- 모델별 부분: 로딩 방식·채팅 템플릿·추론 및 도구 호출 설정

으로 나뉩니다.

### 대부분 공통인 설정

다음 요소는 거의 모든 로컬 LLM에서 확인합니다.

- 모델 크기와 양자화 수준
- GPU·CPU 사용 비율
- 컨텍스트 길이
- 배치 크기
- 온도, `top_p`, 최대 출력 길이
- API 주소와 인증
- 메모리 부족 시 CPU 오프로딩
- 보안 및 파일 접근 권한

하지만 적절한 값은 모델과 하드웨어에 따라 달라집니다.

### 모델마다 달라지는 중요한 부분

#### 1. 모델 파일 형식

같은 모델도 실행 환경에 따라 파일이 다릅니다.

| 환경                            | 일반적인 형식 |
| ------------------------------- | ------------- |
| llama.cpp·LM Studio·일부 Ollama | GGUF          |
| Transformers·vLLM·SGLang        | Safetensors   |
| Apple MLX                       | MLX 변환 모델 |
| 일부 NVIDIA 최적화 환경         | AWQ·GPTQ·FP8  |

GGUF 파일을 vLLM용 명령으로 그대로 실행하거나 MLX 모델을 llama.cpp로 여는 식으로 혼용할 수는 없습니다.

#### 2. 아키텍처 지원 여부

실행 프로그램이 해당 모델 구조를 알아야 합니다.

예를 들어 Qwen3.6의 Gated DeltaNet·MoE·비전 구조를 구형 llama.cpp나 Ollama가 지원하지 않으면:

- 모델 로딩 실패
- 매우 느린 실행
- 이미지 입력 불가
- 잘못된 출력
- GPU 가속 미적용

등이 발생할 수 있습니다. 새 모델을 사용할 때는 실행 프로그램을 최신 버전으로 업데이트하는 이유입니다.

#### 3. 채팅 템플릿

모델은 대화를 내부적으로 특정 형식으로 변환합니다.

개념적으로는 다음과 같은 차이가 있습니다.

```text
<system>...</system>
<user>...</user>
<assistant>...
```

또는

```text
<|im_start|>system
...
<|im_end|>
```

실제 형식은 모델마다 다릅니다. 템플릿이 틀리면 모델은 실행되더라도:

- 지시를 무시하거나
- 이상한 특수 토큰을 출력하거나
- 대화를 계속 반복하거나
- 성능이 크게 떨어질 수 있습니다.

Ollama나 LM Studio가 대부분 자동 처리하지만, 모델 카드의 공식 템플릿과 일치하는지는 확인해야 합니다.

#### 4. Thinking·Reasoning 방식

추론 모델은 각각 제어 방법이 다릅니다.

- 어떤 모델은 `enable_thinking` 같은 API 옵션 사용
- 어떤 모델은 별도의 reasoning 모델 사용
- 어떤 모델은 프롬프트 태그 사용
- 어떤 모델은 thinking을 끌 수 없음
- 일부 모델은 추론 결과를 별도 필드로 반환

Qwen용 thinking 설정을 다른 모델에 그대로 적용하면 무시되거나 출력이 깨질 수 있습니다. 추론 파서도 Qwen, DeepSeek 등 모델 계열에 맞춰 지정해야 합니다.

#### 5. 도구 호출 형식

함수나 터미널 도구 호출 방식도 다릅니다.

- OpenAI 호환 JSON 형식
- XML 형태의 도구 호출
- 전용 특수 토큰
- 모델별 함수 호출 템플릿

따라서 일반 대화는 잘 되지만, 코딩 에이전트에서만 실패하는 경우가 있습니다. 모델과 실행 서버뿐 아니라 사용하는 에이전트 프로그램까지 호환되어야 합니다.

#### 6. 권장 생성 설정

`temperature`, `top_p`, `top_k`, 반복 페널티도 모델별 권장값이 다릅니다.

예를 들어 모든 모델에 `temperature=0`을 적용하면 일부 추론 모델에서는 반복이나 성능 저하가 나타날 수 있습니다. 반대로 코딩 모델에 온도를 너무 높게 설정하면 코드의 일관성이 떨어집니다.

가장 먼저 모델 카드의 권장 설정을 사용하고, 이후 자신의 작업으로 조정하는 편이 안전합니다.

### 같은 모델도 환경에 따라 설정이 달라집니다

예를 들어 Qwen 모델 하나를 실행하더라도:

```text
Qwen 모델
├─ Mac → MLX 또는 llama.cpp
├─ Windows 개인 PC → LM Studio, Ollama 또는 llama.cpp
├─ Linux NVIDIA 서버 → vLLM 또는 SGLang
└─ 여러 사용자 서비스 → vLLM/SGLang + 인증 프록시
```

처럼 달라집니다.

Mac에서는 통합 메모리와 Metal 설정이 중요하고, NVIDIA 환경에서는 CUDA 버전, GPU 분할과 텐서 병렬화가 중요합니다. CPU 환경에서는 스레드 수와 GGUF 양자화가 중요합니다.

### 안전한 설치 순서

새 모델을 사용할 때마다 다음 순서로 확인하면 됩니다.

1. 모델의 공식 모델 카드를 읽습니다.
2. 내 실행 프로그램이 해당 아키텍처를 지원하는지 확인합니다.
3. 환경에 맞는 파일 형식을 선택합니다.
4. 공식 채팅 템플릿을 사용합니다.
5. 공식 권장 생성 설정으로 시작합니다.
6. 작은 컨텍스트로 텍스트 대화를 테스트합니다.
7. 그다음 긴 문맥, 이미지, thinking, 도구 호출을 각각 테스트합니다.
8. 마지막으로 컨텍스트와 GPU 사용량을 올립니다.

결론적으로 **설치의 뼈대는 공통이지만, 모델마다 전용 드라이버를 맞추듯 템플릿·추론 설정·파일 형식·권장 파라미터를 따로 맞춰야 합니다.** Ollama나 LM Studio는 이 차이를 상당 부분 자동화해 주지만 완전히 없애주지는 않습니다.

네, **원칙적으로는 하나금융그룹 자체 클라이언트의 개발·운영 가이드를 최우선으로 따라야 합니다.** 다만 클라이언트 가이드만 보는 것이 아니라, 아래 세 계층을 함께 맞춰야 합니다.

```text
사내 보안·운영 정책
        ↓
자체 클라이언트의 개발 가이드
        ↓
사용 중인 Qwen 모델·추론 서버의 공식 권장값
```

우선순위는 보통 다음과 같습니다.

1. 사내 보안·컴플라이언스 정책
2. 자체 클라이언트가 정의한 인터페이스와 허용 범위
3. 현재 사용하는 Qwen의 정확한 모델 버전
4. vLLM·SGLang·Ollama 등 추론 서버의 설정 규칙

### 클라이언트 가이드를 반드시 따라야 하는 항목

다음 파라미터는 클라이언트가 모델 요청을 변환하거나 제한할 수 있으므로, 사내 가이드가 기준입니다.

- `model` 이름과 버전
- API 엔드포인트와 인증 방식
- `messages` 및 system prompt 구조
- `temperature`, `top_p`
- `max_tokens` 또는 `max_completion_tokens`
- `stop` 조건
- 스트리밍 여부
- 도구·함수 호출 스키마
- Thinking 사용 여부 및 추론 예산
- 타임아웃과 재시도
- 컨텍스트 최대 길이
- 개인정보 마스킹과 로그 저장
- 파일·DB·터미널 접근 권한

예를 들어 Qwen 공식 문서가 `enable_thinking=true`를 지원하더라도, 사내 클라이언트가 이 필드를 차단하거나 자체 필드로 변환한다면 Qwen 공식 예제를 그대로 넣어서는 안 됩니다.

### 그렇다고 클라이언트 가이드만 따르면 충분한 것은 아닙니다

자체 클라이언트의 설정이 Qwen 모델 특성과 충돌할 수도 있습니다. 특히 다음은 모델별 확인이 필요합니다.

- 정확한 모델: Qwen3, Qwen3.5, Qwen3.6 중 무엇인지
- Instruct·Thinking·Coder 등의 모델 종류
- 채팅 템플릿
- Thinking parser
- Tool-call parser
- 공식 권장 sampling 값
- 이미지 입력 지원 여부
- 최대 컨텍스트와 실제 운영 제한
- 양자화 모델 여부
- 추론 서버 버전

클라이언트 가이드에 값이 없을 때만 Qwen 공식 모델 카드의 권장값을 적용하고, 사내 평가를 거쳐 기본값으로 확정하는 편이 안전합니다.

### 금융권에서 특히 고정해야 할 철칙

#### 1. 사용자가 임의로 핵심 파라미터를 변경하지 못하게 하기

업무 화면에서 모든 파라미터를 노출하기보다 서버가 허용 범위를 제한해야 합니다.

예:

```text
temperature: 0.0~0.3
max_tokens: 서비스별 상한 고정
thinking: 승인된 업무에서만 허용
tools: 업무별 허용 목록 적용
timeout/retry: 서버에서 통제
```

정확한 범위는 하나금융 내부 기준과 평가 결과를 따라야 합니다.

#### 2. 모델 버전을 고정하기

다음처럼 `latest` 별칭을 운영에 사용하면 모델 교체 후 결과가 갑자기 달라질 수 있습니다.

```text
qwen-latest
```

대신 내부적으로 검증된 정확한 버전과 양자화·서빙 환경까지 고정해야 합니다.

```text
모델 ID
모델 가중치 체크섬
양자화 버전
채팅 템플릿 버전
추론 서버 버전
클라이언트 버전
기본 파라미터 세트 버전
```

#### 3. 재현 가능한 요청 기록 남기기

감사와 장애 분석을 위해 최소한 다음 정보는 추적할 수 있어야 합니다.

- 요청 ID와 시간
- 업무 유형
- 클라이언트·모델·프롬프트 템플릿 버전
- 적용된 생성 파라미터
- 호출한 도구와 결과 상태
- 필터링·마스킹 여부
- 사용자 승인 이력

단, 원문 프롬프트나 모델 응답에 개인정보·신용정보·인증정보가 포함될 수 있으므로 무조건 전체를 로그에 남기면 안 됩니다. 로그 보존 범위는 내부 보안정책에 맞춰야 합니다.

#### 4. 모델 출력을 명령으로 직접 실행하지 않기

Qwen의 출력은 신뢰할 수 없는 입력으로 취급해야 합니다.

```text
모델 제안
   ↓
형식·정책 검증
   ↓
권한 검사
   ↓
필요 시 사용자 승인
   ↓
실행
   ↓
결과 검증
```

송금, 고객정보 변경, 상품 가입, 권한 변경, 외부 메시지 발송 등 중요한 행위는 모델 판단만으로 실행하면 안 됩니다.

#### 5. 업무별 파라미터 프로파일 만들기

모든 업무에 하나의 공통 설정을 적용하기보다 프로파일을 분리하는 것이 좋습니다.

- 문서 요약: 낮은 온도, 긴 입력, 짧은 출력
- 규정 질의: 낮은 온도, 근거 인용 필수
- 코드 작성: 낮은 온도, 테스트 필수
- 일반 문안 작성: 비교적 높은 온도
- Tool Calling: 낮은 온도, 엄격한 JSON 검증
- 고위험 업무: 모델은 제안만 하고 사람이 승인

### 판단 기준

- **사내 가이드에 명시된 값:** 그대로 사용
- **허용 범위만 명시:** 그 범위 안에서 모델 평가로 결정
- **가이드에 없는 값:** Qwen 공식 권장값으로 시작한 뒤 내부 검증
- **사내 가이드와 Qwen 권장값이 충돌:** 임의로 변경하지 말고 모델 담당팀·클라이언트 담당팀·보안 담당자에게 확인
- **가이드가 현재 모델보다 오래됨:** 적용 가능하다고 가정하지 말고 재검증

따라서 질문하신 내용은 대체로 맞습니다. 다만 정확히는 **“클라이언트 개발 가이드를 무조건 복사한다”가 아니라, 사내 정책을 최상위 기준으로 두고 자체 클라이언트가 보장하는 파라미터 계약을 따르면서 Qwen 버전별 요구사항과 충돌하지 않는지 검증해야 한다”**가 올바른 원칙입니다.
